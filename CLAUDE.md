# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this package is

`mogobase` is a dual-purpose npm package:

1. **A library** consumed by other apps — exports a server runtime (`mogobase/server`), a MongoDB wrapper (`mogobase/db`), and React client hooks (`mogobase`).
2. **A CLI** (`bin: mogobase`) for the caller app's workflows — `mogobase dev` runs the dev server from the consumer's `node_modules`, `mogobase install` copies source files (currently React hooks) into the consumer's tree, and `mogobase mcp` launches the bundled Model Context Protocol server over stdio so AI assistants can drive scaffolding/inspection.

The build output is published as ESM (`"type": "module"`, `exports` map). Sources use TS path alias `@/*` → `./src/*`; `tsc-alias` rewrites these in `lib/` after `tsc`.

## Commands

- `npm run build` — clean `lib/` and compile (`tsc && tsc-alias`), then copy `src/mcp/guides/*.md` into `lib/mcp/guides/` (the MCP resource loader reads them from there at runtime). Runs automatically via `prepublish`.
- `npm run dev` — `wrangler dev` (Cloudflare Workers entrypoint, separate from the Node dev path used by consumers).
- `npm start` — `node lib/server/start.js` (Node runtime).
- `npm run cf-typegen` — regenerate `CloudflareBindings` types from `wrangler.jsonc`.

There are no tests or linters configured. Do not add CI/lint/test tooling without being asked.

## Architecture

### Server (`src/server/`)

- `handlers.ts` — singleton `Handlers` class holds four maps: public `queries`/`mutations` and internal `_queries`/`_mutations`. Public registration uses `query()` / `mutation()`; internal uses `internalQuery()` / `internalMutation()` (stored with `internal.` prefix). Args are zod v4 schemas validated via `safeParseAsync` before calling the handler. The `v` export is `zod/v4`. Public `runQuery`/`runMutation` are thin wrappers over the singleton's `_runQuery`/`_runMutation` — use these from the Next.js route template. **The `MogobaseDB` singleton is read via `globalThis.__mogobase_db__.instance` rather than a static `import` so this module stays browser-safe** (handlers.ts is re-exported from `mogobase/runtime`, which the offline hooks consume; a static `import DB from "@/db"` would pull `mongodb` into the client bundle). The singleton publishes itself to `globalThis` the moment `mogobase/db` is loaded on the server.
- Handler `ctx` always includes `db`, `runQuery`, `runMutation`, `headers`, `useDatabase`, `useRawDatabase`, and (for queries) `watch`. `runQuery`/`runMutation` bind back into the singleton so handlers can invoke each other, including `internal.*` names; recursive `runQuery`/`runMutation` calls set an internal `_resolved: true` flag on the inherited ctx so the per-request DB resolver does not re-run. The `watch` signature is `(modelName, pipelineOrFilter?, options?) => void`. The second arg is the **aggregation pipeline you would pass to `collection.watch(pipeline)`**, normalized through `src/server/watchInput.ts` — accepted shapes: a single `$match` stage object (e.g. `{ $match: { "fullDocument.userId": x, operationType: "insert" } }`), a full pipeline array (multi-stage all-`$match` pipelines stay on the streamHub fast path; any non-`$match` stage like `$project` falls back to a per-socket `collection.watch(pipeline)`), or a bare doc filter (`{ userId: x }`) which is auto-translated to `{ $or: [{ "fullDocument.userId": x }, { operationType: "delete" }] }` so deletes still notify the subscriber. The streamHub evaluates the `$match` filter in JS against the **full change event** (paths are native: `fullDocument.<field>`, `operationType`, `documentKey._id`, …). The third arg is forwarded as `ChangeStreamOptions`.
- **Per-request DB resolution.** Before running a handler, `_runQuery`/`_runMutation` check `if (ctx.db === dbSingleton && !ctx._resolved)` and call `dbSingleton._resolveActive(ctx.headers)` once at the entry boundary. If a resolver is registered (`DB.setRequestResolver(...)`) and returns a string, `ctx.db` becomes a `MogobaseDBView` bound to that database name (same cluster); `null`/`undefined` keeps the default singleton. Resolver throws surface as `DB resolver threw …`. The resolved DB flows through to all recursive `ctx.runQuery`/`ctx.runMutation` calls via `_resolved: true` so the resolver only fires once per request even across nested handler calls.
- **Multi-DB ctx members.** `ctx.useDatabase(dbName: string)` returns a `MogobaseDBView` for a different database on the **default cluster** (same `MONGO_URI`). Views share `_schemas` with the singleton, so every `defineModel(...)` call is visible across views; indexes are applied lazily per `(uri, dbName, modelName)` on first model access. In a mutation handler, the result is wrapped with `wrapDbWithAutoStamp` so writes pick up the same timestamping + `dbValidation` semantics as `ctx.db`. `ctx.useRawDatabase(name: string)` is async and returns a raw `mongodb.Db` for a connection registered via `DB.registerDatabase(name, { uri?, dbName })` — used for cross-cluster reads (e.g. analytics on a different URI). Raw DBs are NOT autoStamp-wrapped and have no `dbValidation`. Both helpers throw at call time if the registry / singleton isn't available (e.g. running outside the server runtime).
- `attachWs.ts` — `attachMogobaseWebSocket(httpServer, path="/ws", options?)` public helper. Takes the caller's Node `http.Server` and attaches a `ws` `WebSocketServer` for the given upgrade path. Routes incoming `{ type: "query" | "paginated-query" | "paginated-query-load-next" | "paginated-query-load-previous" | "mutation" | "sync-subscribe" | "sync-pull" | "sync-push" }` messages through the singleton handlers and pushes back `QueryResult` / `PaginatedQueryResult` / `PaginatedQueryPage` / `MutationResult` / `SyncPullResult` / `SyncPushResult` / `sync-stream` frames. The optional third arg accepts `{ syncPolicy }` and forwards it to every `pullChanges` / `pushChanges` / `streamChanges` invocation. This is what the Next.js custom-server template wires up. Upgrade interception is done via `server.emit` shadowing rather than `server.on("upgrade")` so Next's own upgrade handler doesn't double-respond on our path (which previously corrupted the socket and closed with 1006).
  - `useQuery` path: each `ctx.watch(...)` opens a `DB.model(name).watch()` change stream scoped to the socket; every change triggers a full handler re-run and a fresh `QueryResult` frame.
  - `usePaginatedQuery` path: the server keeps **one** `PaginatedSub` per socket holding `loadedCount`, `changeStreams: ChangeStream[]` (one per `ctx.watch` call), a serialization `queue: Promise<void>`, the upgrade `headers`, pagination args, and stored `nextCursor` / `previousCursor`. Every change event calls `scheduleRefetch`, which chains through `sub.queue` and re-runs the handler with `paginationOpts.limit = sub.loadedCount`, emitting a fresh `PaginatedQueryResult`. `paginated-query-load-next/previous` runs through the same queue with the stored cursor, then updates `loadedCount += rs.results.length`. Listener attachment is deferred until after the initial handler run completes and the sub is installed in `state`, so the scheduler always sees a registered sub (events emitted during the initial run are buffered by Mongo and delivered once listeners attach).
  - Sync path: `sync-subscribe` opens one `streamChanges(models, …)` per socket (stored as `syncUnsub` on `SocketState`, cleaned up on `close`); each Mongo change emits a `sync-stream` frame back to the client. `sync-pull` calls `pullChanges({model, checkpoint, batchSize, headers})` and replies with `SyncPullResult`. `sync-push` calls `pushChanges({model, rows, headers})` and replies with `SyncPushResult` carrying any conflicts.
- `sync.ts` — server sync engine consumed by `attachWs.ts`, `ws.ts`, `hono.ts`, and the optional `app/api/sync/route.ts` HTTP-fallback template. Exports `pullChanges` (numeric `updatedAt`-checkpointed query that **does not** filter `deletedAt: null` — it must propagate tombstones), `pushChanges` (per-row `findOne` + last-writer-wins by `updatedAt`, returns server doc as conflict if remote is newer), and `streamChanges(models, onEvent, opts?)` (one Mongo change stream per model, returns a single cleanup fn). All timestamps on the wire are numeric ms (`Date.now()`); ISO strings are not used. Missing `updatedAt` falls back to `createdAt` then epoch (retrofit for pre-sync collections). The engine enforces a layered security model:
  - **Default-deny model allowlist.** Every entry point asserts `getModelOptions(model).sync === true` (set via `defineModel(name, schema, { sync: true })`). Unconfigured models throw `Model "X" is not configured for sync` before any IO. Models declared with `timeseries: {...}` throw `Model "X" is a time-series collection. Sync is not supported …` at the same boundary — time-series collections have no soft-delete tombstone semantics, so they are mutually exclusive with sync (`defineModel` also rejects the combination up-front).
  - **`SyncPolicy` callback.** Each operation calls `syncPolicy({ op, model, headers })` (`op` is `"pull" | "push" | "watch"`) and expects `{ allow, filter?, transform? }`. `allow: false` returns `Forbidden`. `filter` is merged into the pull query (`$and` with `updatedAt > checkpoint`) and translated to a change-stream `$match` pipeline (`filterToWatchPipeline` prefixes keys with `fullDocument.` for `streamChanges`). Policy throws are logged as `[mogobase/sync] policy threw …` and converted to `{allow: false}`.
  - **`clientFields` projection.** Pull projects each doc to `clientFields ∪ {_id, createdAt, updatedAt, deletedAt}` (the `CLIENT_ENGINE_FIELDS` constant). Push strips the inverse — any non-allowlisted key in a client row is dropped before storage.
  - **Server-owned timestamps.** Push always overrides client `createdAt`/`updatedAt`/`deletedAt` with the server clock so a malicious client can't rewrite history or backdate writes.
  - **`transform(doc, existing)`.** Optional per-row hook from the policy decision, called inside `pushChanges` with the about-to-write payload and the current server doc. Throwing converts the row into a conflict (server doc preserved, no write); returning a new object lets the policy force ownership fields (e.g. `userId`) on every create and reject cross-tenant updates.
  - **Push batch cap.** `pushChanges` enforces `MAX_PUSH_BATCH = 500` rows per request; over-cap calls return `{conflicts: rows.map(...)}` without writing.
- `autoStamp.ts` — `wrapDbWithAutoStamp(db)` Proxy used inside both `_runMutation` and `_runQuery` so the Decimal128 read-decode applies on every code path (queries previously skipped wrapping, which leaked raw `Decimal128` instances to JSON-serialized query results — those serialize to `{"$numberDecimal":"…"}` and silently break consumers that expect `.toString()`-form strings). Write-stamping branches are gated on the write op name and are dead code on read-only query handlers. It transparently stamps `updatedAt: Date.now()` on `updateOne`/`updateMany`, adds `createdAt`+`updatedAt`+`deletedAt:null` on `insertOne`/`insertMany`, and rewrites `deleteOne`/`deleteMany` into `$set: {deletedAt: now, updatedAt: now}` so the sync checkpoint catches deletions. Handlers that need a true hard-delete must reach through `ctx.db.model(name).collection.deleteOne(...)` directly. When the model has `dbValidation: true`, the same wrapper validates each write against the model's zod schema **after stamping** (so engine timestamps are present in the validated payload) and **before** the underlying call: `insertOne`/`insertMany` and full-replace updates run as full-doc parses; `$set` and `$setOnInsert` run as partials; aggregation-pipeline updates are skipped (no generic way to statically check the result shape). Validation failures throw `[mogobase] Validation failed for <model>.<op>: <path: msg; …>` synchronously — `await coll.insertOne(...)` in a handler catches it as a normal rejection. **For time-series models** (`isTimeseries(name) === true`), the wrapper changes shape: inserts skip the `deletedAt:null` stamp (still adds `createdAt`/`updatedAt`); `deleteOne`/`deleteMany`/`findOneAndDelete` always pass through to MongoDB's native delete regardless of `sync` (timeseries models are sync-incompatible by definition). **Decimal128 codec.** When a model's schema declares one or more `v.decimal128()` fields (`schemaHasDecimal128`), the same wrapper transparently encodes canonical decimal strings → BSON `Decimal128` on writes (schema-guided: `insertOne`/`insertMany`/full-replace docs, plus `$set`/`$setOnInsert` operator and dotted-path keys; **after** validation so the zod check still sees the string) and decodes `Decimal128` → string on reads (schema-agnostic deep walk over `findOne`/`findOneAndUpdate`/`findOneAndDelete` results and lazily through `find`/`aggregate` cursors, so the wire/handler form stays a plain decimal string while MongoDB stores the true numeric type — numeric `$gt`/`$sum`/`$avg`/cross-type comparison just work). Models with no decimal field skip both walks entirely (zero overhead). Codec primitives live in browser-safe `src/runtime/decimal.ts`; only the autoStamp wrapper imports `Decimal128` from `mongodb`.
- `hono.ts` — legacy HTTP app used by the standalone dev server (`mogobase dev`). Same `/api/handlers` GET/POST shape, plus `/api/sync` POST (`?action=pull|push`) that delegates to `pullChanges` / `pushChanges`.
- `ws.ts` — legacy Hono WebSocket wiring used by `mogobase dev`. Same message protocol as `attachWs.ts`, including the three sync message types.
- `start.ts` — Node entry for `mogobase dev`. Loads `.env` / `.env.local` from cwd, scans `./mogobase/` for `.ts` files, imports each, and calls its default export with the Hono `app`. Port from `MOGOBASE_PORT` (default `4000`). **This is only used when consumers want a standalone mogobase server — the Next.js path (`server.ts` template) replaces this.**

### DB (`src/db/`)

- `index.ts` — `MogobaseDB` singleton. `connect()` uses `MONGO_URI` / `MONGO_DB` (defaults `mongodb://localhost:27017` / `mogobase`). `defineModel(name, schema?, options?)` creates the collection if missing, stores the schema in `_schemas`, registers `options` (`indexSpecs`, `clientFields`, `sync`, `timeseries`) in `_options`, and applies indexes — including unconditional `{updatedAt:1}`, `{deletedAt:1}`, `{createdAt:1}` indexes that the sync checkpoint depends on (Mongo no-ops on duplicate creates; **skipped for time-series models**, see below). Exports: default singleton, `Id` (`ObjectId`), `buildFilters` (from `buildMongoFilters`), and `DataLoaderGenerate(model, key="_id")` for batched lookups. The singleton publishes itself to `globalThis.__mogobase_db__.instance` on load so the browser-safe `src/server/handlers.ts` can read it without a static import (see Server section).
- **Time-series collections.** When `defineModel` is called with `timeseries: { timeField, metaField?, granularity?, bucketMaxSpanSeconds?, bucketRoundingSeconds?, expireAfterSeconds? }`, the internal `_applyModelToDb` path probes for the collection via `listCollections({name}, {nameOnly: true})` and — only if it does not yet exist — calls `dbHandle.createCollection(name, { timeseries: {...}, expireAfterSeconds })`. Existing non-timeseries collections of the same name are left alone (MongoDB cannot convert a regular collection into a timeseries one); the create error is logged as `failed to create timeseries collection …` and mogobase falls back to a regular handle. The auto sync-checkpoint indexes (`updatedAt`, `deletedAt`, `createdAt`) are intentionally skipped for timeseries models — sync is disallowed, and the metaField+timeField auto-index covers the common access pattern. Custom `indexSpecs` are still applied. Timeseries options flow through the same `onModel`-listener path as schemas: `runtime/models.ts:defineModel` puts them on the `ModelDef`, the listener forwards them to `db/index.ts:defineModel(name, schema, indexes, timeseries)`, and `MogobaseDBView.defineModel` accepts the same fourth argument so multi-DB consumers can declare timeseries on a view. Helpers `getTimeseriesOptions(name)` and `isTimeseries(name)` from `mogobase/runtime` expose the registry state to the autoStamp and sync layers.
- **Multi-database primitives.** The singleton holds five additional registries: `_clients: Map<uri, MongoClient>` (one pooled connection per URI, reused across views), `_views: Map<key, MogobaseDBView>` (cached views keyed by `${uri}::${dbName}`), `_rawAliases: Map<name, { uri, dbName }>` (named cross-cluster connections registered via `registerDatabase`), `_appliedModels: Map<key, Set<modelName>>` (per-DB lazy-index dedup), and `_resolver?: RequestResolver` (the optional per-request hook).
  - `setRequestResolver(fn | null)` — registers/clears the resolver. Signature: `(ctx: { headers?: any }) => string | null | undefined | Promise<…>`. Called once per request from `_runQuery`/`_runMutation`'s entry boundary via `_resolveActive(headers)`. Returning a string binds `ctx.db` to a view of that DB name on the default cluster; `null`/`undefined` keeps the singleton; throws are wrapped as `DB resolver threw …`.
  - `useDatabase(dbName)` — synchronous; returns a `MogobaseDBView` for the named DB on the default cluster. Uses the cached view if present, else creates one via `_getOrCreateView(uri, dbName)` which calls `_getOrConnectClient(uri)` (lazy `MongoClient.connect`) and stores it in `_views`.
  - `registerDatabase(name, { uri?, dbName })` — registers a named raw alias. `uri` defaults to the singleton's URI when omitted (rare; `useDatabase` already covers same-cluster). Throws if `name` is already registered.
  - `useRawDatabase(name)` — async; resolves the alias to a raw `mongodb.Db` via the same `_getOrConnectClient` pool. Throws `Raw database "<name>" is not registered` if the alias is missing. No autoStamp, no schema awareness — it is the unwrapped driver.
  - `_resolveActive(headers)` — internal. Runs the resolver (if any) and returns either the singleton or a `MogobaseDBView`. Wrapped in try/catch so resolver throws surface as `DB resolver threw <err>`.
  - `_ensureModelApplied(view, modelName)` — internal. Idempotent per `(uri, dbName)` set in `_appliedModels`; on first call for a model on a given DB, replays the schema's indexes against that DB's collection. Called from `MogobaseDBView.model(name)` so cold-path cost is bounded to the first access of each (DB, model) pair.
  - **`MogobaseDBView`** — lightweight wrapper sharing `_schemas` (and therefore `_options` / `getModelOptions`) with the singleton. Exposes `client`, `db`, `model(name)`, `defineModel(...)` (delegates to the singleton so registration stays global), `getSchema` / `getSchemas`. Tests rely on `(view as any).db._name` to read the bound database name.
  - **No sync support.** The sync engine still uses the singleton's default DB; `useDatabase` and `useRawDatabase` are server-side reads/writes only. Multi-tenant sync is out of scope for v1.

### Runtime registry (`src/runtime/models.ts`)

- `defineModel(name, schema?, options?)` runs `withSyncFields(schema)` before storing the def. `withSyncFields` merges `{createdAt: v.number(), updatedAt: v.number(), deletedAt: v.number().nullable()}` into either a `ZodObject` (via `.extend`) or a plain shape object — sync timestamp fields **always override** any consumer-defined versions of those keys. Schema-less models receive just the three sync fields. This is what guarantees that handler authors don't have to declare timestamps and that the RxDB JSON-schema generator + WatermelonDB JSON-blob both see numeric timestamps for every model.
- `options` is `{ indexSpecs?, clientFields?, sync?, dbValidation?, timeseries? }`. The runtime registry stores the full options object alongside the schema and exposes `getModelOptions(name)` so both the server sync engine and the `filterClientFields` runtime util can read `clientFields` and the `sync: true` allowlist flag from a single source of truth. `timeseries: { timeField, metaField?, granularity?, bucketMaxSpanSeconds?, bucketRoundingSeconds?, expireAfterSeconds? }` opts the underlying collection into MongoDB time-series mode — `defineModel` rejects `sync: true` combined with `timeseries` at registration with `defineModel("X"): \`sync: true\` is incompatible with \`timeseries\`` because soft-delete tombstones can't propagate through time-series collections. `getTimeseriesOptions(name)` / `isTimeseries(name)` expose the flag to the autoStamp wrapper (skip `deletedAt:null` stamp on inserts, skip soft-delete rewrites on deletes) and the sync engine (reject pull/push/watch). `clientFields: string[]` is the visibility allowlist for both the sync engine (pull projection + push strip) and the `filterClientFields` runtime helper. `sync: true` is the explicit opt-in required by the default-deny sync gate. `dbValidation: true` opts the model into runtime validation of writes (default false): the autoStamp wrapper parses each insert/update payload against the model's zod schema and throws on type mismatch — see `autoStamp.ts` below. The registry also exposes `isValidationEnabled(name)` and `getModelZodSchema(name)` (which normalizes plain shape objects into `z.object(...)` so callers can `.parse()` or `.partial()` uniformly). **Auto-loader caveat**: the `npx mogobase install` template's `server.ts` only scans `./mogobase/*.ts` — if `sync: true` lives only in a file under `./mogobase-sync/`, the server never sees the opt-in and the sync engine throws `Model "X" is not configured for sync`. Either keep the `defineModel` call under `./mogobase/`, or extend the loader to walk both folders.
- `v.decimal128()` (in `src/runtime/decimal.ts`, attached to the `v` export from `src/server/handlers.ts`; zod/v4's default export is non-extensible so `v` is `{ ...z4, decimal128 }`, not a mutation of `z4`) — a branded zod string validating a canonical decimal string (`-?\d+(\.\d+)?`) that the autoStamp wrapper persists as a BSON `Decimal128` and reads back as a string (see `autoStamp.ts`). The brand is a `Symbol.for("mogobase.decimal128")` on the schema instance; it survives `.optional()`/`.nullable()` because those wrap (not copy) the inner instance and `isDecimal128Schema` unwraps `_def.innerType`. `decimal.ts` is browser-safe (no `mongodb` import) — it only walks schemas/values; the real `Decimal128` constructor is injected by the server-side wrapper. Exposes `isDecimal128Schema` / `schemaHasDecimal128` / `encodeDecimal128` / `encodeDecimal128Patch` / `decodeDecimal128Deep`.
- `filterClientFields(model, input)` (in `src/runtime/clientFields.ts`, re-exported from `mogobase/runtime`) — projects an online handler's return value through the same allowlist used by sync. Reads `getModelOptions(model).clientFields`; if undefined, returns `input` unchanged. Otherwise projects to `clientFields ∪ CLIENT_ENGINE_FIELDS`. Handles three input shapes: single doc → projected doc; array → array of projected docs; paginated `{results, hasNext, hasPrevious, next, previous}` → same shape with `results` projected. The intent is symmetry: setting `clientFields` once on `defineModel` covers both the WS/HTTP query path (via `filterClientFields` calls in handlers) and the sync transport (automatic).

### Runtime helpers (`src/runtime/env.ts`, `src/runtime/paging.ts`)

- `env.ts` — `isServer()` / `isClient()` based on `typeof window === "undefined"`. Used by isomorphic handlers to dispatch on runtime; `isServer()` is true in Node (Next.js custom server, route handler workers, SSR) and false in any browser context.
- `paging.ts` — browser-safe polyfill of `mongo-cursor-pagination`'s default-exported `MongoPaging.find(col, params)`. Operates on any `find(filter).toArray()`-shaped collection (`RxMongoAdapter`, `WatermelonMongoAdapter`). Pulls the full matched set, then sorts/filters/slices in JS — adequate for per-user offline / sync datasets, not for million-row server queries. Same return shape as upstream (`{results, previous, next, hasPrevious, hasNext}`); cursor tokens are `base64url(JSON.stringify(value))` (plain JSON, not BSON-EJSON), with the standard `_id`-cursor → encoded value, non-`_id` cursor → `[fieldValue, _id]` shape. Supports `paginatedField`, `sortAscending`, `sortCaseInsensitive`, `next` / `previous`, `fields` projection, dotted-path field access. Mirrors upstream's `prepareResponse` semantics for `hasPrevious` / `hasNext`. The `find` function is exported both via `export const MongoPaging = { find }` and `export default MongoPaging` so handlers can use either named or default-import patterns. **Polyfill cursors and upstream BSON-EJSON cursors are not interchangeable**, but each side stays consistent within its own page sequence — which is all the hook needs.

Both helpers are re-exported from `mogobase/runtime`. The intended pattern for paginated handlers that run in both modes is:

```ts
import { isServer, MongoPaging as MongoPagingPolyfill } from "mogobase/runtime"
import MongoPaging from "mongo-cursor-pagination"
const Pager = isServer() ? (MongoPaging as any) : MongoPagingPolyfill
return Pager.find(ctx.db.model(name), { query, paginatedField: "_id", ...paginationOpts })
```

### Client (`src/client/`)

- `hooks/` — React hooks (`useQuery`, `useMutation`, `usePaginatedQuery`). The routing rule across all three: `if (online && !sync) → WS/HTTP`; `else if (ready && clientDB) → run handler against clientDB and re-run on clientDB.observeChanges(name)`. The fallback branch is reused for both `online={false}` and `online && sync` — same `runQuery` / `runMutation` from `mogobase/server` (pure, browser-safe). The hooks never import any backend module — they read `clientDB` and `sync` from React context. URLs are same-origin (derived from `window.location`), with `NEXT_MOGOBASE_URL` / `MOGOBASE_URL` env override for SSR or split-origin deploys. Also compiled into `lib/` and re-exported from the package root.
- `sync-types.ts` — wire-protocol types shared by client and server: `SyncDoc` (numeric `updatedAt`, `deletedAt`, `_deleted` flag), `SyncPullResult`, `SyncPushResult`, `SyncOptions` (`wsUrl`, `getAuth`, `models`, `conflictResolver`, `batchSize`), `SyncHandle` (`status`, `cancel`, `onStatusChange`). All timestamps are numeric ms. Browser-safe — no Node imports.
- `provider.ts` — `MogobaseProvider` / `useMogobase` context. Takes `online`, `handlers` (async loader), `dbName`, `clientDB`, `sync` (default `false`), and `syncOptions`. The provider holds **zero references** to either offline backend — direct or dynamic. The boot effect treats `useClientDB = !online || (online && sync)` as the trigger to run `clientDB.connect(dbName)`, the handler loader, and replay `getModels()` into `clientDB.defineModel(...)`. After ready, when `online && sync`, it calls `clientDB.startSync(syncOptions)` and stores the `SyncHandle` in a ref so it can be cancelled on unmount or dep change. Throws a clear error if the path needs `clientDB` but none was provided. **`syncOptions` is in the effect's dep array — callers must memoize it (module scope or `useMemo`) to avoid tearing down + restarting sync on every render.** `MogobaseClientDB` is exported as a structural type that includes optional `startSync` / `stopSync` so importing it does not pull rxdb / watermelon into the bundle.
- `db/` — pluggable offline backends. The top-level `db/index.ts` re-exports the RxDB backend so consumers can `import RxClientDB from "mogobase/client-db"`.
  - `db/rxdb/` — `MogobaseClientDB` + `RxMongoAdapter` over RxDB + Dexie. `observeChanges(name)` wraps `collection.$` for reactivity.
  - `db/watermelon/` — `MogobaseWatermelonDB` + `WatermelonMongoAdapter` + `filters.ts` (JS-side Mongo matcher + update applier). Each model is one table with `data` (JSON blob) + `deleted_at` (indexed) columns; filters are evaluated in JS on the decoded blob. `observeChanges(name)` wraps `Database.withChangesForTables([name])` and **skips the replay-on-subscribe emission** so `useQuery` doesn't loop on mount. WatermelonDB requires all `defineModel` calls to occur **before** the DB is first accessed; `defineModel` throws if called after `_ensureDb()` for an unknown model, but is idempotent for already-registered models (safe under React strict-mode double-mount).
    - **Cross-tab sync**: unlike RxDB (which has its own BroadcastChannel layer), LokiJS is purely in-memory per tab and doesn't observe IndexedDB peer writes. To fix this, `MogobaseWatermelonDB` opens a `BroadcastChannel("mogobase-watermelon-<dbName>")`. Every adapter mutation (`insertOne`/`insertMany`/`updateOne`/`updateMany`/`deleteOne`/`deleteMany`/`hardDeleteOne`) posts `{ table, op: "upsert", doc }` or `{ table, op: "hardDelete", id }` after writing. Incoming messages are applied through `_applyUpsert` / `_applyHardDelete` on the target adapter — these helpers look up the record by id directly (bypassing the soft-delete filter so a peer's `deletedAt` can travel through), and set `_applyingRemote = true` around the write to prevent echo loops. The resulting Watermelon write fires `withChangesForTables([name])` in the receiving tab so `observeChanges` subscribers (including `useQuery`) refresh naturally. No conflict resolution — last-writer-wins by message order.
- Both backends conform to the same interface: `connect(dbName)`, `defineModel(name, schema?, indexes?)`, `model(name)` → Mongo-shaped adapter, `observeChanges(name)`, `startSync(options)` / `stopSync()` (sync mode), default export = singleton. Hooks reach into neither backend's internals. Both `rxdb` and `@nozbe/watermelondb` are **optional peer dependencies** — only the consumer that actually imports `mogobase/client-db` (or `…/watermelon`) needs to install the matching package. An online-only consumer (no `sync`, no offline) installs neither.
- `db/rxdb/sync.ts` — RxDB sync engine. Uses `replicateRxCollection` from `rxdb/plugins/replication` (dynamically imported, kept out of the base bundle). One shared `WebSocket` to `/ws`; per collection, a `rxjs.Subject` feeds the replicate stream — `"RESYNC"` triggers a re-pull. Pull/push handlers send `sync-pull`/`sync-push` over WS and resolve when the matching `SyncPullResult`/`SyncPushResult` arrives (multiplexed by `model` field). Checkpoint flows through RxDB as `{ts: number, updatedAt: number}` and is unwrapped to a plain numeric ms internally. WS close → reject pendings, RESYNC every subject, reconnect after 3s.
- `db/watermelon/sync.ts` — WatermelonDB sync engine. Uses `synchronize()` from `@nozbe/watermelondb/sync` (dynamic import). One shared WS, per-model checkpoint `Map<string, number | null>` (we ignore `synchronize`'s single `lastPulledAt` and use our own per-model). **Critical detail**: `synchronize` only fires on WS open and incoming `sync-stream` events — it has no built-in observer for local mutations. To push user writes promptly, the engine subscribes to `wdb.withChangesForTables(targetModels)` and triggers `runSync()` on each emission, with two guards: `inSyncCycle` (set true around `synchronize` so the pull-apply path's writes don't re-trigger a sync) and a `primed` flag (skips `withChangesForTables`'s replay-on-subscribe value). Two known limitations: (1) `synchronize` writes through Watermelon's internal `_applyChanges`, bypassing `WatermelonMongoAdapter` — so sync-applied writes do NOT post to the cross-tab `BroadcastChannel`. Each tab pulls independently, by design. (2) `synchronize` does a full pull per cycle; for >10K records per model the initial sync is slow.
- `api/handlers/route.ts` — Next.js App Router route template. **In-process**: imports `runQuery` / `runMutation` from `mogobase/server` and the `DB` singleton from `mogobase/db`, calls them directly.
- `api/sync/route.ts` — Next.js HTTP-fallback route template for sync. `POST /api/sync?action=pull|push` body `{model, checkpoint?, batchSize?, rows?}`. Imports `pullChanges` / `pushChanges` from `mogobase/server/sync` and forwards a `syncPolicy` arg on every call. The scaffolded template ships with a placeholder `getSession` and a deny-all `syncPolicy`; consumers must wire in their real auth + policy before enabling sync (typically by importing the same `mogobase/syncPolicy.ts` module that `server.ts` uses). Default sync transport is WS; this route exists for environments where WS is unavailable. Always copied by `mogobase install` (harmless when sync isn't enabled).
- `server.ts` — Custom Next.js server template. Creates Node `http.Server`, delegates to Next.js `getRequestHandler()`, calls `attachMogobaseWebSocket(server)`, and loads consumer's `./mogobase/*.ts` files at boot to trigger handler registration. This file is excluded from `tsc` compilation (imports `next` which is a peer dep) and shipped as raw source.
- All four (`hooks/`, `api/handlers`, `api/sync`, `server.ts`) ship as raw `.ts` source via `files` in `package.json` so `mogobase install` can copy them into the caller.

### Dev CLI (`src/dev/`)

- `index.ts` — `bin` entry. Dispatches on first arg: `dev` spawns `npx tsx watch ./node_modules/mogobase/lib/dev/start.js` in the consumer's cwd; `install` calls `install.ts`; `mcp` dynamically imports `../mcp/start.js` to boot the stdio MCP server.
- `install.ts` — `install(options)` is the callable entrypoint used by both the CLI and the MCP `mogobase_install` tool. Takes `{ cwd?, logger? }` and returns an `InstallSummary` (`created` / `overwritten` / `skipped` / `nextSteps`). Copies four things into the caller's Next.js project:
  1. Hooks → prefers existing `src/hooks/` or `hooks/`, else creates `src/hooks/` (or `hooks/` if no `src/`). Rewrites relative imports (`../provider`, `../../runtime`) to package imports via `rewriteHookImports`.
  2. Handlers route → installs to `src/app/api/handlers/route.ts` if `src/app/` exists, else `app/api/handlers/route.ts`.
  3. Sync route → `src/app/api/sync/route.ts` (or `app/api/sync/route.ts`). Always copied even if sync isn't used — harmless idle.
  4. Custom server → `server.ts` at project root.
  Also creates `./mogobase/` folder for consumer's handler files. Files are **overwritten unconditionally** — no interactive prompting; call `mogobase_check_setup` first (or inspect before running) to avoid clobbering.
- Path resolution: `resolveMogobaseRoot()` probes `../..` and `../../..` relative to the running module so it works both from `lib/dev/` in a published install and from source during local tests.

### MCP server (`src/mcp/`)

- `start.ts` — boots an `McpServer` from `@modelcontextprotocol/sdk` with `{ resources, tools, prompts }` capabilities and connects it over `StdioServerTransport`. Name/version come from `readPackageVersion()` (reads the installed `mogobase` `package.json`). Entered via `mogobase mcp`.
- `tools/index.ts` — registers five tools:
  - `mogobase_install` — thin wrapper around `install()` from `src/dev/install.ts`; captures `logger` lines and returns them alongside the `InstallSummary`.
  - `mogobase_check_setup` — reports project type, presence of `server.ts` / route handler / `./mogobase/` / `<MogobaseProvider>` mount, `package.json` scripts+deps, and `MONGO_URI` / `MONGO_DB` across `.env*` files. Non-destructive; always call this before `mogobase_install`.
  - `mogobase_list_handlers` / `mogobase_list_models` — use `parseHandlers.ts` (a regex/AST-light scanner over `./mogobase/*.ts`) to enumerate `query`/`mutation`/`internalQuery`/`internalMutation` calls and `defineModel` calls with file + line.
  - `mogobase_inspect_handler` — returns ~30 lines of source context around a named handler. Accepts either `name` or `internal.name`.
- `resources.ts` — registers nine markdown guides at `mogobase://guide/<slug>` (`overview`, `setup`, `handlers`, `models`, `hooks`, `provider`, `offline-backends`, `sync`, `troubleshooting`). Reads from `lib/mcp/guides/` when installed, falls back to `src/mcp/guides/` during local dev — so the build script must copy `src/mcp/guides/*.md` into `lib/mcp/guides/`. The `sync` guide is the source of truth for the security model (default-deny allowlist, `clientFields` projection, `SyncPolicy` callback, server-owned timestamps, push batch cap, soft-delete invariant).
- `prompts.ts` — registers one prompt, `setup-mogobase`, that seeds the assistant with the correct onboarding workflow (check setup → read guides → propose + confirm → install).
- `guides/*.md` — source of truth for the long-form explanations surfaced via MCP resources. Prefer editing these over inlining large blocks of prose into tool descriptions.
- When adding a new tool, register it from `tools/index.ts` and keep the tool name prefixed with `mogobase_` for easy disambiguation in the MCP client. When adding a new guide, update the `GUIDES` array in `resources.ts` **and** ensure the `.md` file lands in `lib/mcp/guides/` via the build script (no separate `files` entry is needed — the copy step places it inside `lib/`).

### How a consumer uses this package (Next.js App Router)

1. `yarn add mogobase ws` and `yarn add -D @types/ws`. For offline or sync mode, also install the backend you want to use: `yarn add rxdb` (RxDB, default) or `yarn add @nozbe/watermelondb` (WatermelonDB). Pure-online consumers install neither.
2. `npx mogobase install` — copies hooks, `app/api/handlers/route.ts`, `app/api/sync/route.ts`, and `server.ts`; creates `./mogobase/`.
3. Update `package.json` scripts: `"dev": "tsx server.ts"`, `"start": "NODE_ENV=production tsx server.ts"`.
4. Add handler files in `./mogobase/*.ts` that call `query()`/`mutation()` at module scope.
5. Set `MONGO_URI` / `MONGO_DB` in `.env.local`.
6. Pick a provider mode:
   - **Online only**: `<MogobaseProvider online={true}>` — no `clientDB`, no offline package.
   - **Offline only** (`online={false}`): `<MogobaseProvider online={false} clientDB={RxClientDB} handlers={…} dbName="…">`. Hooks run handlers in the browser against `clientDB`.
   - **Local-first sync** (`online={true}` + `sync={true}`): `<MogobaseProvider online sync clientDB={…} handlers={…} dbName="…" syncOptions={…}>`. Hooks read/write through `clientDB`; a background engine continuously replicates with MongoDB over `/ws`. **Memoize `syncOptions`** — it's in the boot effect's dep array. Server-side: every model that participates must be declared with `defineModel(name, schema, { sync: true, clientFields: [...] })`, and `server.ts` must call `attachMogobaseWebSocket(server, "/ws", { syncPolicy })` with a real policy (the same module is imported by `app/api/sync/route.ts` for the HTTP fallback). Without these, the engine returns `Model not configured for sync` or `Forbidden`.

## Conventions specific to this repo

- Singletons are the norm (`Handlers`, `MogobaseDB`, `WebSocket`). Do not introduce per-request instances without a clear reason — existing code relies on the singletons being shared across `hono.ts`, `ws.ts`, and consumer-registered handlers.
- Handler names beginning with `internal` are routed to the `_queries`/`_mutations` maps and stored with an `internal.` prefix — preserve this behavior when editing `handlers.ts`.
- **Timestamps on the wire and in storage are numeric ms (`Date.now()`), never ISO strings.** `createdAt`, `updatedAt`, and `deletedAt | null` are auto-injected on every model by `withSyncFields` in `runtime/models.ts` and auto-stamped on every write by `wrapDbWithAutoStamp` (server) and the client adapters. Don't reintroduce string timestamps; the sync checkpoint and the RxDB JSON-schema bounds (`minimum: 0`, `maximum: 8640000000000000`, `multipleOf: 1`) all assume numbers.
- `_id` for sync-mode collections is a string (UUID from the client adapter's `genId()`). MongoDB collections used with sync must accept string `_id`; existing collections with `ObjectId` `_id` are incompatible.
- When adding files that must be shipped as source (not compiled), update the `files` array in `package.json` — compiled output only covers what `tsc` emits into `lib/`.
- The `baseUrl`/`rootDir` deprecation warnings from `tsc` are pre-existing and do not block `build`; leave them alone unless explicitly asked to migrate.
- **Sync is default-deny.** Adding sync to a model requires three changes that must travel together: (1) `defineModel(name, schema, { sync: true, clientFields: [...] })` on the **server** side (i.e. inside a `./mogobase/*.ts` file the custom `server.ts` actually imports — not split off into `./mogobase-sync/`), (2) a `SyncPolicy` branch returning `{allow: true, filter, transform}` for the model, and (3) the policy module wired into both `attachMogobaseWebSocket(..., { syncPolicy })` and the HTTP fallback `app/api/sync/route.ts`. Skipping any one is the single most common cause of "client gets 403 on every pull".
- **`clientFields` is a contract.** Once set, server-only fields never reach the client (pull-side projection) and clients can't write them (push-side strip). The same allowlist drives `filterClientFields(model, doc)` in online handlers, so adding a new field that should be visible client-side requires updating `clientFields` — it won't simply leak through.
- **Server-owned timestamps.** `pushChanges` always overrides client `createdAt`/`updatedAt`/`deletedAt` with `Date.now()` (or preserves `existing.createdAt` for updates). Don't try to round-trip these through the client.
- **`dbValidation` is gated to handler writes only.** The flag wraps writes that go through `_runMutation`'s autoStamp Proxy. Sync push (`pushChanges` in `src/server/sync.ts`) writes to the raw collection and is **not** validated by this flag — it relies on the policy `transform` callback for shape enforcement. So a model can have `dbValidation: true` for handler safety while still depending on `transform` to gate sync-push payloads.
- **Time-series models are sync-incompatible and have reduced auto-stamp.** `defineModel(name, schema, { timeseries: { timeField, … } })` makes mogobase create the collection via `db.createCollection(name, { timeseries: {…} })` on first apply (and skip the `updatedAt`/`deletedAt`/`createdAt` auto-indexes — they are not needed because sync is forbidden). The autoStamp wrapper stops adding `deletedAt: null` to inserts and passes `deleteOne` / `deleteMany` / `findOneAndDelete` straight through to MongoDB. Sync entry points (`pullChanges`, `pushChanges`, `streamChanges`) reject timeseries models with `Model "X" is a time-series collection. Sync is not supported …`. `buildMongoFilters` still works transparently — the `{deletedAt: null}` predicate it always injects matches docs that don't have the field. `mongo-cursor-pagination` paginates timeseries collections correctly by `_id`. **You cannot convert an existing regular collection into a timeseries one** — `createCollection` errors when a non-timeseries collection of the same name already exists; drop or rename it first.
