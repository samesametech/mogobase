# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this package is

`mogobase` is a dual-purpose npm package:

1. **A library** consumed by other apps — exports a server runtime (`mogobase/server`), a MongoDB wrapper (`mogobase/db`), and React client hooks (`mogobase`).
2. **A CLI** (`bin: mogobase`) for the caller app's workflows — `mogobase dev` runs the dev server from the consumer's `node_modules`, `mogobase install` copies source files (currently React hooks) into the consumer's tree, and `mogobase mcp` launches the bundled Model Context Protocol server over stdio so AI assistants can drive scaffolding/inspection.

The build output is published as ESM (`"type": "module"`, `exports` map). Sources use TS path alias `@/*` → `./src/*`; `tsc-alias` rewrites these in `lib/` after `tsc`.

## Commands

- `npm run build` — clean `lib/` and compile (`tsc && tsc-alias`), then copy `src/mcp/guides/*.md` into `lib/mcp/guides/` (the MCP resource loader reads them from there at runtime). Runs automatically via `prepublish`.
- `npm run dev` — `wrangler dev` (Cloudflare Workers entrypoint, separate from the Node dev path used by consumers).
- `npm start` — `node lib/server/start.js` (Node runtime).
- `npm run cf-typegen` — regenerate `CloudflareBindings` types from `wrangler.jsonc`.

- `npm test` — unit then integration tests (vitest). `npm run test:unit` (`vitest.unit.config.ts`, `tests/unit/**`, no database) and `npm run test:integration` (`vitest.integration.config.ts`, `tests/integration/**`, against a real single-node replica set started by `mongodb-memory-server` in `tests/setup/integrationGlobalSetup.ts`, so change streams work; files run one at a time, `maxWorkers: 1`, each in a fresh fork). `npm run test:watch` watches the unit suite. A fix comes with a test that fails without it.

There is no linter or CI configured. Do not add CI/lint tooling without being asked.

## Architecture

### Server (`src/server/`)

- `handlers.ts` — singleton `Handlers` class holds four maps: public `queries`/`mutations` and internal `_queries`/`_mutations`. Public registration uses `query()` / `mutation()`; internal uses `internalQuery()` / `internalMutation()` (stored with `internal.` prefix). Args are zod v4 schemas validated via `safeParseAsync` before calling the handler; a refusal throws a plain `Error` (`invalidArgs`) whose message is `Invalid args: ` + every issue as `<path>: <msg>` joined by `; `, first issue first, at most 10 listed then `; …and N more` (a root-level issue has no path), with the structured `issues: { path, code, message }[]` on the error (`InvalidArgsError` / `ArgsIssue` types). Keep it a plain `Error`: the HTTP route template answers with `${error}`, and consumers match the `Invalid args: ` prefix. The `v` export is `zod/v4`. Public `runQuery`/`runMutation` are thin wrappers over the singleton's `_runQuery`/`_runMutation` — use these from the Next.js route template. **The `MogobaseDB` singleton is read via `globalThis.__mogobase_db__.instance` rather than a static `import` so this module stays browser-safe** (handlers.ts is re-exported from `mogobase/runtime`, which the offline hooks consume; a static `import DB from "@/db"` would pull `mongodb` into the client bundle). The singleton publishes itself to `globalThis` the moment `mogobase/db` is loaded on the server.
- Handler `ctx` always includes `db`, `runQuery`, `runMutation`, `headers`, `useDatabase`, `useRawDatabase`, and (for queries) `watch`. `runQuery`/`runMutation` bind back into the singleton so handlers can invoke each other, including `internal.*` names; recursive `runQuery`/`runMutation` calls set an internal `_resolved: true` flag on the inherited ctx so the per-request DB resolver does not re-run, and a nested `runQuery` carries the caller's `watch`, so a query a live handler calls registers its watches on the same run — in the database it runs against when given a `db` of its own (`nestedWatch` adds that `dbName`; the watch's own `dbName` still wins; the caller's own database, even passed back as `ctx.db`, adds nothing, so a model's home still decides). The `watch` signature is `(modelName, pipelineOrFilter?, options?) => void`. The second arg is the **aggregation pipeline you would pass to `collection.watch(pipeline)`**, normalized through `src/server/watchInput.ts` — accepted shapes: a single `$match` stage object (e.g. `{ $match: { "fullDocument.userId": x, operationType: "insert" } }`), a full pipeline array (multi-stage all-`$match` pipelines stay on the streamHub fast path; any non-`$match` stage like `$project` falls back to a per-socket `collection.watch(pipeline)`), or a bare doc filter (`{ userId: x }`) which is auto-translated to `{ $or: [{ "fullDocument.userId": x }, { operationType: "delete" }] }` so deletes still notify the subscriber — any plain non-stage object is a bare filter, including one with a top-level `$expr` (its fields are prefixed too; inside `$expr` write `$fullDocument.field` — deliberate and documented in the handlers guide, unlike sync's policy filter, which is also a pull filter); such a filter runs on a stream of its own. A watch using `$where`, `$text` or `$near`/`$nearSphere`, which no change stream runs (`unstreamableOperator` in `watchInput.ts`), goes to the hub unnarrowed — the whole collection (`routeWatchInput` answers `{ kind: "hub", matchFilter: undefined, unnarrowed }`; ws.ts an empty pipeline), warned once per (collection, operator) by `warnUnnarrowed`: on a stream of its own MongoDB refused it every attempt, retried for good, and the query never updated; unnarrowed costs re-runs, never secrecy (the handler decides what is sent). The streamHub evaluates the `$match` filter in JS against the **full change event** (paths are native: `fullDocument.<field>`, `operationType`, `documentKey._id`, …). The third arg is forwarded as `ChangeStreamOptions` to a watch's own change stream, minus mogobase's own keys (`ignoreFields`, `dbName`, `paginatedField`, `sortAscending`) and `fullDocument`/`fullDocumentBeforeChange` (set by the transport; a pre-image is never read, and asking for one can kill the watch) (split off by `splitWatchOptions` in `src/server/changeStreamWatch.ts`, which both transports use to open such streams). `ignoreFields: string[]` (normalized by `normalizeIgnoreFields`, which adds `updatedAt`) skips update events whose changed paths (`updatedFields` keys, `removedFields`, `truncatedArrays`) all equal or lie under an ignored field (`touchesOnlyIgnored` in `watchInput.ts`); inserts/deletes always pass, and a `replace` event (no updateDescription) too — a replace made through the autoStamp wrapper is an update pipeline, which usually arrives as an `update` whose changed fields are checked like any update's. It is part of the watch key, applies on the hub (per subscriber, `subscribe(..., { ignoreFields })`) and on own streams, and is opt-in: no option, no change.
- `streamHub.ts` — one shared change stream per `(database, model)`, subscribers matched in JS (`filterMatcher`). Each open stream holds one pooled connection (its awaitData getMore), so streams per process = watched models × databases, plus one per subscriber for watches routed to a stream of their own; `scaling.md` says to size `maxPoolSize` (driver default 100) above that. Default mode: `openStream(dbName, model)` with no spec → attachWs opens `watch([], { fullDocument: "updateLookup" })`, exactly as before. **Server-filter mode** (`createStreamHub({ serverSideFilters: true })`, exposed as `attachMogobaseWebSocket(..., { serverSideWatchFilters: true })`, default off): `openStream(dbName, model, { pipeline, fullDocument, startAfter? })` where `currentSpec`/`buildSpec` build one `$match` OR-ing the distinct subscriber filters, each through `toServerMatch` (a logical `$not` becomes `$nor`) — none if any subscriber is unfiltered, and `fullDocument` is true only if some filter reads `fullDocument.*` (`referencesFullDocument`). Bookkeeping is refcounted per slot (`filters` map of distinct filter keys → count, `everything`, `docReaders`), so subscribe/unsubscribe is O(1) and only a membership change schedules a reopen. A subscriber the open stream does not cover (`covers(slot.opened, sub)`) goes into `slot.pending` with the stream's `resumeToken` at its join (undefined when no stream/no token yet); covered subscribers are never tracked, so no token in `pending` is older than a reopen delay. `scheduleReopen` (one timer per slot, `reopenDelayMs` default 50; a request while one is scheduled joins it; never sooner than `reopenNotBefore` after a failed reopen; cancelled by the last unsubscribe and `shutdown`; unref'd) opens a new stream resuming `startAfter` the earliest pending join token (else the old stream's `resumeToken`), attaches it (a replaced stream stops dispatching: handlers check `slot.stream === stream`; `attach` removes the pending subscribers it covers — one that joined mid-reopen stays pending for the next, and one the old stream covered but the new one does not is made pending with the reopen's `startAfter`) and closes the old one. Pending subscribers with no token, or everyone if there is no resume point at all, get `"resync"`. A failed reopen clears pending tokens (they will resync) and retries. A subscribe while the slot sleeps out its reconnect backoff opens nothing (the reconnect opens the stream and resyncs everyone). **Both modes:** a stream that errors OR closes without the hub asking (an invalidate after a drop/rename) is detached at once and reconnects (a reconnect already running sees it gone and keeps trying: only a stream still attached once started ends the loop; a reopen counts as done only once its stream started); reconnect backs off (`reconnectDelayMs` doubling to 30 s) while the slot has subscribers, `failures` resets on any change or after a stream lived 60 s, and at the 3rd consecutive failure subscribers get `"error"` once (a live query does NOT treat it as its watch's death — `onChangeOrResync`, used by live queries and sync streams alike: the hub keeps reconnecting on its backoff and resyncs everyone once back; an engine retry would unsubscribe and resubscribe at once and, for the last subscriber, reset the slot's backoff). After a reconnect both modes resync every subscriber (the new stream starts after whatever was written during the backoff). A failed reopen (server mode) backs off the same way (`reopenFailures` → `reopenNotBefore`, which a subscribe or unsubscribe in the meantime cannot cut short) and sends `"error"` on the 3rd in a row. `SubscriberCallback` types: change types, `"error"` (informational: three failures in a row, the hub is still reconnecting and will resync everyone once back — live queries and sync streams ignore it), `"resync"` (re-read). **A stream counts as open only once it runs on the server:** `streamStarted` (`changeStreamWatch.ts`) waits for its first `resumeTokenChanged` (a fresh stream gets one with the empty first batch that answers its `$changeStream` aggregate), or its end, or `STREAM_START_TIMEOUT_MS` (10 s); `openChangeStreamWatch` awaits it, and the hub awaits it through `whenReady` (attachWs passes `streamStarted`) before a subscribe resolves (`slot.ready`, joiners included) and before a resync after a reconnect or a reopen — `collection.watch()` returns before the aggregate runs, so a read made in between missed a write the stream never reported. After a reconnect, subscribers the new stream does not cover yet stay pending (token cleared) for the reopen, which resyncs them once it covers them; a reopen skipped while the reconnect ran is scheduled again when it ends.
- **Per-request DB resolution.** Before running a handler, `_runQuery`/`_runMutation` check `if (ctx.db === dbSingleton && !ctx._resolved)` and call `dbSingleton._resolveActive(ctx.headers)` once at the entry boundary. The resolver — and every sync policy call, all through `evaluateSyncPolicy` (`sync.ts`, exported: both WebSocket transports, hono.ts's sync route, the sync route template; a throwing policy is a logged refusal) — gets its headers through `headerView` (`src/server/headers.ts`, exported from `mogobase/server` and `mogobase/server/sync`): one shape from every door — a real Fetch `Headers` (a copy: `instanceof Headers`, the native methods; before 4.0.0 the HTTP doors and ws.ts passed the request's own `Headers`, and a plain-object view broke auth helpers that check for one) carrying one enumerable lowercase key per header as Node's IncomingHttpHeaders — accessors over the Headers' own list, so a `.set`/`.delete` and a plain write stay in step — a value being its `get()` string (set-cookie its list) (a name or value Fetch refuses, an HTTP/2 pseudo-header, is a plain key only; a header named like a member — `get`, `keys`, `constructor` — leaves the member and is read with `get(name)`); a snapshot built per call (not cached by object: a reused headers object then answered with its first values), the WebSocket transports building one per socket, and each live-query run (its resolver call and its handler) and each sync policy call getting a copy of it (`copyHeaders`: on the socket's one view, a handler's `ctx.headers.set` reached every later run on the socket and the DB resolver) — since HTTP hands over a Fetch `Headers` and attachWs a plain object, and a resolver written for one read nothing on the other. Handlers' own `ctx.headers`: a `headerView` on both WebSocket transports (attachWs builds it once per socket), the route's Fetch `Headers` over HTTP (kept a real `Headers`: apps pass it to auth libraries) — so `ctx.headers.get(name)` works on every transport. If a resolver is registered (`DB.setRequestResolver(...)`) and returns a string, `ctx.db` becomes a `MogobaseDBView` bound to that database name (same cluster); `null`/`undefined` keeps the default singleton. Resolver throws surface as `DB resolver threw …`. The resolved DB flows through to all recursive `ctx.runQuery`/`ctx.runMutation` calls via `_resolved: true` so the resolver only fires once per request even across nested handler calls.
- **Multi-DB ctx members.** `ctx.useDatabase(dbName: string)` returns a `MogobaseDBView` for a different database on the **default cluster** (same `MONGO_URI`). Views share `_schemas` with the singleton, so every `defineModel(...)` call is visible across views; indexes are applied lazily per `(uri, dbName, modelName)` on first model access. In a mutation handler, the result is wrapped with `wrapDbWithAutoStamp` so writes pick up the same timestamping + `dbValidation` semantics as `ctx.db`. `ctx.useRawDatabase(name: string)` is async and returns a raw `mongodb.Db` for a connection registered via `DB.registerDatabase(name, { uri?, dbName })` — used for cross-cluster reads (e.g. analytics on a different URI). Raw DBs are NOT autoStamp-wrapped and have no `dbValidation`. Both helpers throw at call time if the registry / singleton isn't available (e.g. running outside the server runtime).
- `messages.ts` — `handleMessage(raw, transport)`: the WebSocket protocol's routing (JSON parse, load messages, sync-subscribe/pull/push, name required, query/paginated-query, mutation refusal, unknown type), shared by both transports; a transport passes only its socket wiring (`send`, `live`, `syncState`, `syncPolicy`, `syncHub`, `formatError`).
- `attachWs.ts` — `attachMogobaseWebSocket(httpServer, path="/ws", options?)` public helper. Takes the caller's Node `http.Server` and attaches a `ws` `WebSocketServer` for the given upgrade path. Routes incoming `{ type: "query" | "paginated-query" | "paginated-query-load-next" | "paginated-query-load-previous" | "mutation" | "sync-subscribe" | "sync-pull" | "sync-push" }` messages and pushes back `QueryResult` / `PaginatedQueryResult` / `PaginatedQueryPage` / `SyncPullResult` / `SyncPushResult` / `sync-stream` frames. A `mutation` message is **refused** on both transports with `mutationRefusedFrame` (a `MutationResult` with `success: false` naming the fix: mutations go to `POST /api/handlers`, which is what `useMutation` does); an unknown type gets `unknownTypeFrame`; a handler error in a message never becomes an unhandled rejection (both transports `.catch` the message handler). The optional third arg accepts `{ syncPolicy }` and forwards it to every `pullChanges` / `pushChanges` / `streamChanges` invocation. This is what the Next.js custom-server template wires up. Upgrade interception is done via `server.emit` shadowing rather than `server.on("upgrade")` so Next's own upgrade handler doesn't double-respond on our path (which previously corrupted the socket and closed with 1006).
  - Live queries (`query`, `paginated-query`, the two load messages) are handled by the shared engine in `src/server/liveQuery.ts` (`createLiveQueries`), used by both `attachWs.ts` and the legacy `ws.ts`; the transport supplies `resolveActive`, `watchSpec` (one `ctx.watch` call → a spec with a `key`; attachWs routes `$match`-only filters to the shared `streamHub` and other pipelines to a per-socket `collection.watch`, ws.ts uses per-socket streams only) and `openWatch`. **Subscriptions live in slots** (4.0.0): a `query`/`paginated-query` without `sid` uses the socket's default slot (one subscription, a new one replacing it — the pre-4.0 behaviour, unchanged); one with a client-chosen `sid` (`readSid`: a string ≤ 64 chars or a finite number; an unusable one is refused, never taken for the default) gets or replaces the slot for that sid, `unsubscribe { sid }` removes it (acked `Unsubscribed`; `slot.ended` stops every later frame for it), and every frame for it echoes `sid` (`framePayload`, the one frame builder; `withRid` echoes rid and sid on the transports' own refusals). A slot (`Slot`) owns its subscription's watches, deaths/openFailures, openedAt, specs, retry timers, catch-up flag, backpressure `dirty` mark and run `queue`; a failed run tears down (and removes) only its slot; siblings watching the same filter each hold their own watch (hub refcounts stay right). Runs are serialized per slot; the handler runs (with their resolver call) of one socket take at most `maxConcurrentRunsPerSocket` (default 4) turns at once (`withTurn`; not held across the watch opens after a run, which can wait seconds on a cold stream); a failure frame that ends a sid's subscription carries `ended: true` (`endedMark`; sent right after teardown's synchronous part — the slot leaves the socket at once — and before the watch closes are awaited, which finish in the background, so a re-subscribe of the sid meanwhile is never the one it ends) — any other failure for a sid (a replaced subscription's own answer, a load) answers one request; the default slot's frames carry no `ended`; `sid: null` means no sid; a run of an unsubscribed slot or a closed socket is skipped before it starts and again once it gets a turn (`skipped`), so queued handlers never run for nobody; a turn held past `turnTimeoutMs` (default 5000; above setTimeout's 2^31-1 ms, Infinity included, no timeout) is given up — at most `maxConcurrentRunsPerSocket` runs over time at once (`overtime`), past which a run keeps its turn and tries again a timeout later —; the three limits and `maxRerunRows` go through `limitOf` (not a number ≥ 1 → default, warned: a NaN run cap hung every run; taken whole — a fractional `maxRerunRows` reached the pager as a page limit); each slot has its own scheduler key (`runKey`, not the sid's, so a re-subscribed sid's re-runs never wait on the unsubscribed one's run); a paginated re-run stops reading pages once its subscription is replaced; runs a client asked for (first runs, loads) wait ahead of change-triggered re-runs (`waitingAsked`), and a paginated re-run takes a turn per page; the legacy ws.ts takes the limits — and `maxRerunRows`, `maxBufferedBytes`, by attachWs's names; any other key, `refetchMaxWaitMs` included (no debounce there to bound), warned and ignored — through `ws.setLiveQueryOptions(...)`; re-runs are debounced per slot (scheduler key: the slot's own `runKey`, `socketId\u0000<sequence>`); `maxSubscriptionsPerSocket` (default 32 — about 3× the ~10 live queries of a busy tab, a third of the driver's default pool — the default slot included) refuses a new slot with an error frame carrying its sid; a slot removed by a failed run leaves its queue as the key's `tail` until it settles, so a reused sid's frames never overtake the old one's (an unsubscribed slot sends nothing more and leaves none); every removed slot whose run is still going counts toward the limit until it settles or for at most 15 s (`lingering`, `LINGER_LIMIT_MS` — watch opens, what it is counted for, wait at most 10 s), so a subscribe/unsubscribe loop cannot hold more opens than the cap and a hung removed run cannot hold a place for good; closing a socket resumes the runs waiting for a turn, which find it closed and skip, so every chain settles. A failed run answers through `failRun` (teardown first, frame, closes in the background); `subscribe` and `teardown` share `resetSlotState`. Replacing a slot's subscription (`subscribe` on a slot that has one) makes the new one follow the old one's run, waiting for it at most `turnTimeoutMs` (`waitAtMost`): unbounded, a handler that never settled left every later subscription on the slot unanswered (on main each subscription had its own queue); a replaced subscription's run never touches the slot's watches, so overlapping is safe — and a replacement that stops waiting starts a new queue generation (`slot.chain`): a change-triggered re-run queued on an older one is skipped, since it reads `slot.sub` when it starts and ran the replacement beside the replacement's own runs (two runs of one subscription, the watch opened twice and one never closed; `openOne` also keeps the first of two concurrent opens of one key and closes the second). A per-slot AbortSignal, or a fresh slot per subscription, replacing `skipped`/`lingering`/`tails` is a possible follow-up, not done. Numeric options go through `numberOption` (`refetchDebounceMs`, `refetchMaxWaitMs` in the engine; `maxBufferedBytes`, `heartbeatMs` in attachWs): not a number ≥ its minimum → its default, with a warning. The protocol guide (`src/mcp/guides/protocol.md`) documents every message and frame. **Every run** — first run, each change-triggered re-run, each loaded page — collects the handler's watches, and after the run **succeeds** the socket's open watches are reconciled to that set by key (new ones open first, then dropped ones close; unchanged ones stay open, so no churn). A loaded page *adds* its watches; the next re-run replaces the set. When a subscription that was already live opens a watch it did not have in a re-run (a filter built from what the run read, or a dead watch reopened), `catchUpAfter` schedules one more run, since the read preceded the watch and a write in between went unseen; a catch-up run never schedules another (no loop for a watch that changes every run). A subscription's first run and a loaded page are not caught up (deliberate: the first would double every subscribe, the second would re-read the whole window on every page load). `subscribe()` resets the catch-up flag, cancels the replaced subscription's retry timers and clears its specs. A real change (`onEvent`: a watch event, a reopened watch, a drained buffer) clears a pending catch-up flag, so a run it is merged into may schedule a catch-up of its own; the catch-up itself is scheduled with `scheduleRun`, which leaves the flag set. Retry and reconnect waits come from one `backoffDelay` (`src/server/backoff.ts`: 1 s doubling to 30 s; `STABLE_LIFE_MS` 60 s forgets old failures) used by the engine, the hub and sync streams of their own. A watch that fails to open, dies before it ever started (a pipeline the server rejects: a failed open, no catch-up), or dies on its own (`onDead`) is dropped and **reopened by itself** from its spec (`s.specs`, the subscription's wanted watches) — `retryWatch` → `reopenWatch`: at once, then 1 s doubling to 30 s (deaths and failed opens counted apart; an event from the watch, or the watch having lived `stableWatchMs` (60 s) before dying, resets it; pending retry timers are tracked in `retryTimers` and cleared on teardown and on a new subscription). Only once it is open again does the subscription re-run, reading what it missed — so a watch that can never start costs an open attempt per backoff, not a handler run and a frame. A failed run of the current subscription — a re-run or a page load — tears it down (all watches closed — fail closed, never register before success: handlers call `watch()` before their auth gate). **Backpressure** (per socket): a transport's `LiveConnection.isBackedUp()` (attachWs: `ws.bufferedAmount > maxBufferedBytes`, default 1 MiB; ws.ts: the raw socket's, 1 MiB) holds change-triggered re-runs — no handler run, no frame — marking each slot a change reached `dirty`, and `holdUntilDrained` puts the socket in the engine's one `backedUp` set, polled by a single timer every 100 ms (`DRAIN_POLL_MS`), re-running each dirty slot once when it drains; requested runs are always answered. Runs/reconciles of a slot are serialized through its queue; change events go through `refetchScheduler` (debounced per slot, `refetchDebounceMs` 100; a burst still runs every `maxWaitMs` / attachWs `refetchMaxWaitMs`, default 1000) and re-run whatever the slot's subscription is when the run starts. A run a client asked for is always answered, even if superseded — unless a newer subscription on the slot has answered first (possible only once a replacement stopped waiting for it, `waitAtMost`): then it is dropped (`answeredGen`), so a client without rids never shows an old query's rows under new arguments; a change-triggered re-run of a superseded subscription is dropped. Re-runs and page loads pass the client's paginationOpts minus its per-page keys (`pageOpts`: paginatedField, fields, sort, …) unchanged, and a re-run starts where the window starts (`start`: the first page's `next` cursor, or `{ previous, count }` — the `count` rows before a cursor, for a window that began before one or grew upward with loadPrevious, which moves it; read back a page at a time walking backward, since `count` can exceed a page), then walks `next`. When nothing is left on the window's side of its start (every row before a `previous` start, or after a `next` start, deleted or filtered out — the pager then answers an empty page with no cursor to continue from), the window is read from the top and the start forgotten (`onFromTop`): it came back empty, wiping the client's list with load-more stuck on empty pages. A client that sends no (or a non-numeric) `limit` gets the handler's own page size: `sub.limit` is set from the first page (`limitAsked`). Paginated re-runs re-read `Math.max(loadedCount, limit)` rows — capped at `maxRerunRows` (default `DEFAULT_MAX_RERUN_ROWS` 1000, never below the first page; past it the frame has the first `maxRerunRows` rows and `hasNext: true`, so the client's list shrinks and loadNext continues from the cap; a window that grew upward past the cap — a `{ previous, count }` start with `count` over it — keeps the cap's rows nearest its starting cursor, with `hasPrevious: true`, since reaching its first rows means reading every row above them) — through `readWindow`, in pages of at most `RERUN_PAGE_LIMIT` (300 — mongo-cursor-pagination clamps any `limit` to its `MAX_LIMIT`), walking the `next` cursor and answering in one page's shape (`previous`/`hasPrevious` from the first page, `next`/`hasNext` from the last); the handler runs once per page and its watches are the union of the pages'. Every request may carry an optional `rid` (`readRid`: a string ≤ 200 chars or a finite number); it becomes the subscription's current rid (a load message updates it when the load runs, not when it arrives, so a queued load is answered with its own), and every answer frame carries the rid current when the run producing it **started** — so a client can tell the answer it asked for after a write from one already in flight. No `rid` in, no `rid` out. Transports echo it on their own answer frames too (`withRid`: name-required, unknown-type, refused mutation). Watch keys use `filterKey` for the filter (`stableStringify.ts`: a filter's conditions and operators sorted, the members of `$in`/`$nin`/`$all` in a stable order (sets), values compared by equality — an embedded document, `$eq`, each set member — in their own key order, since MongoDB matches embedded documents in order; the hub's server-filter keys use it too) and `stableStringify` for the rest, which handles `ObjectId`/`Date`/`RegExp` (they used to all print as `{}`).
  - Sync path (shared by both transports through `src/server/syncMessages.ts`: `syncSubscribe`, `evaluateSyncPolicy`, `syncPullFrame`, `syncPushFrame`, `syncDbName`; ws.ts subscribes on `syncHub()`, the hub `streamChanges` uses): `sync-subscribe` subscribes each allowed model (all at once, deduplicated; the default-deny gate `requireSyncEnabled` runs before the policy is asked, so an undeclared model costs no policy call) through `subscribeSyncStream` (`sync.ts`), which is **default-deny like pull and push** (`requireSyncEnabled`: a model not declared `sync: true`, or a time-series one, never streams — the watch path used to check only the policy, which allows everything when unset) — narrowed by the policy's filter (`syncChangeMatch`: the filter on `fullDocument.*` only — field paths, `$$ROOT` and `$$CURRENT` inside its `$expr` moved there too (`prefixFilterWithFullDocument(filter, true)`; not inside a `$let` that rebinds CURRENT), since the same filter is a document filter for pull — NOT OR'd with deletes as a live query's is — sync deletes are soft, and a hard delete carries no document to tell its tenant by) AND any spec pipeline, routed by `routeWatchInput` (`watchInput.ts`, the same rule attachWs's live-query watches use; its pipeline result carries a `reason` — `operator $elemMatch`, `stage $project` — and its `$match` stages go through `toServerMatch`, which rewrites a top-level `$not` (JS-matcher-only) as `$nor`; `warnOwnStream` logs once per (collection, reason) that each subscriber gets a stream, and so a pooled connection, of its own) to the hub, or to a change stream of its own when the hub's JS matcher cannot run it ($elemMatch, $expr, a non-$match stage), which reopens itself (1 s doubling to 30 s) when it ends on its own and, once a reopen has started (one that dies while starting is closed and retried, no pull), tells the client to pull — from both transports through `syncSubscribe` (attachWs on its own hub, ws.ts on `syncHub()`, the hub the exported `streamChanges` also uses; `streamChanges` specs honour `filter` and `pipeline` — it used to ignore them and stream every change, so on ws.ts every client heard of every tenant's writes), always in the **default database** — the one `pullChanges`/`pushChanges` read and write, whatever the request resolves to — stored as `syncUnsub` on the socket state and ended by `endSync` on `close` and in attachWs's `stop()` (which also closes every client socket with 1001 and ignores messages after it, since `wss.close()` leaves client sockets open); each matching change emits a `sync-stream` frame. A model whose stream fails to open (MongoDB unreachable at subscribe), or whose policy threw (`policyThrew`), is retried on `backoffDelay`, policy asked afresh, until it opens (the client is then told to pull) or the subscription ends — by `openSyncStreamRetrying` (`sync.ts`), which `syncSubscribe` and the exported `streamChanges` share (`streamChanges` used to give up on the first failure); a model not declared for sync (`requireSyncEnabled` throws a `SyncRefusedError`, which is how a refusal is told from a failure), or a policy's `allow: false`, is refused, not retried. `evaluateSyncPolicy` reads a policy answer that is not an object (a fallthrough returning nothing) as a logged denial. Each sync-subscribe bumps `syncGen` and stores its unsubscriber at once (stored only once every model's first open settled, one model's hanging policy left it unset, and the socket's close could not end the models already open); only the newest one keeps its subscriptions (an older one finishing late, or one whose socket closed, unsubscribes itself). `sync-pull` replies with `SyncPullResult`, `sync-push` with `SyncPushResult` carrying any conflicts.
- `sync.ts` — server sync engine consumed by `attachWs.ts`, `ws.ts`, `hono.ts`, and the optional `app/api/sync/route.ts` HTTP-fallback template. Exports `pullChanges` (numeric `updatedAt`-checkpointed query that **does not** filter `deletedAt: null` — it must propagate tombstones; a full batch also takes the rest of its last `updatedAt` group, past `batchSize`, since the next pull asks for rows after the checkpoint and a soft `deleteMany` stamps every row with one `updatedAt` — cut inside the group, the rest was never pulled), `pushChanges` (per-row `findOne` + last-writer-wins by `updatedAt`, returns server doc as conflict if remote is newer), and `streamChanges(specs, onEvent)` (one shared hub stream per model in the default database, or a stream of its own for a filter the hub cannot run; returns a single cleanup fn). All timestamps on the wire are numeric ms (`Date.now()`); ISO strings are not used. Missing `updatedAt` falls back to `createdAt` then epoch (retrofit for pre-sync collections); a pull makes index-range `find()`s — never an aggregation, whose `$match` refuses a policy filter's `$where`/`$near` (round F19's broke every pull of such a policy, and scanned the collection on every pull) — each sorted on its one field (a two-field sort was done in memory) and limited to a batch, merged, completed and checkpointed by `pageKey` (exactly what the reads select by: a numeric `updatedAt`, a Date `updatedAt`, else a numeric `createdAt`, else 0 — ordered by `pickEffectiveTimestamp` instead, rows no read selects had a place in the order, and main's first pull returned rows this did not; the wire's `updatedAt` is still `pickEffectiveTimestamp`'s): `updatedAt` a number; `updatedAt` a Date (`engineTimestamp` accepts one; a numeric `$gt` never matches a Date; a checkpoint past the Date range, `MAX_DATE_MS`, skips the Date read — `new Date(since)` invalid made it a ping-pong); no `updatedAt`, by a numeric `createdAt`; and on a pull from the start a string `updatedAt` (page key 0, as main's `{}` returned). Rows with page key 0 come only on a pull from the start, at most a batch; `probeUnpageable` (positive index brackets — a `$not` branch scanned every row with no `updatedAt` — at most once a minute per model, off the pull's path) warns once with a chunked `updateMany` stamping them with `$$NOW` (their own old date would leave them behind a client's checkpoint). A group at key 0 is not completed; a completed group is appended row by row (spread into `push`, a group past ~100 000 rows overflowed the stack and every pull threw); the checkpoint is the last page key, never 0 for a row (0 reads as "from the start": a batch of unstamped rows was pulled again for ever). A pull during a long bulk write gets the rows written so far and never the rest (main too; a settle delay on checkpoints would close it — not in 4.0.0; the sync guide says to delete in chunks). `pickEffectiveTimestamp` reads a BSON number too (Decimal128, Long). The checkpoint never answers 0 for a row (0 reads as "from the start": a batch of unstamped rows was pulled again for ever). The engine enforces a layered security model:
  - **Default-deny model allowlist.** Every entry point asserts `getModelOptions(model).sync === true` (set via `defineModel(name, schema, { sync: true })`). Unconfigured models throw `Model "X" is not configured for sync` before any IO. Models declared with `timeseries: {...}` throw `Model "X" is a time-series collection. Sync is not supported …` at the same boundary — time-series collections have no soft-delete tombstone semantics, so they are mutually exclusive with sync (`defineModel` also rejects the combination up-front).
  - **`SyncPolicy` callback.** Each operation calls `syncPolicy({ op, model, headers })` (`op` is `"pull" | "push" | "watch"`) and expects `{ allow, filter?, transform? }`. `allow: false` returns `Forbidden`. `filter` is merged into the pull query (`$and` with `updatedAt > checkpoint`) and translated to a change-stream `$match` (`syncChangeMatch`: every field path under `fullDocument.`, inside `$or`/`$and`/`$nor` and `$expr` too, and a `$jsonSchema` applied to `fullDocument` (`prefixFilterWithFullDocument`: passed through, it was checked against the event, which never satisfies a document's schema); the deprecated public `filterToWatchPipeline` prefixes the same way but fails closed — a filter a change stream cannot run stays, since its caller may stream whole documents; a filter using `$where`/`$text`/`$near`, which a change stream refuses, leaves the stream unnarrowed through `routeWatchInput`, as a live-query watch's, with a warning once — a `sync-stream` frame names the model only, and each pull applies the whole filter). Policy throws are logged as `[mogobase/sync] policy threw …` and converted to `{allow: false}`.
  - **`clientFields` projection.** Pull projects each doc to `clientFields ∪ {_id, createdAt, updatedAt, deletedAt}` (the `CLIENT_ENGINE_FIELDS` constant). Push strips the inverse — any non-allowlisted key in a client row is dropped before storage.
  - **Server-owned timestamps.** Push always overrides client `createdAt`/`updatedAt`/`deletedAt` with the server clock so a malicious client can't rewrite history or backdate writes.
  - **`transform(doc, existing)`.** Optional per-row hook from the policy decision, called inside `pushChanges` with the about-to-write payload and the current server doc. Throwing converts the row into a conflict (server doc preserved, no write); returning a new object lets the policy force ownership fields (e.g. `userId`) on every create and reject cross-tenant updates.
  - **Push batch cap.** `pushChanges` enforces `MAX_PUSH_BATCH = 500` rows per request; over-cap calls return `{conflicts: rows.map(...)}` without writing.
- `autoStamp.ts` — `wrapDbWithAutoStamp(db)` Proxy used inside both `_runMutation` and `_runQuery` so the Decimal128 read-decode applies on every code path (queries previously skipped wrapping, which leaked raw `Decimal128` instances to JSON-serialized query results — those serialize to `{"$numberDecimal":"…"}` and silently break consumers that expect `.toString()`-form strings). Write-stamping branches are gated on the write op name and are dead code on read-only query handlers. It transparently stamps `updatedAt: Date.now()` on `updateOne`/`updateMany`, adds `createdAt`+`updatedAt`+`deletedAt:null` on `insertOne`/`insertMany`, and rewrites `deleteOne`/`deleteMany` (and `findOneAndDelete`, bulkWrite's deletes) on a sync model into `$set: {deletedAt: now, updatedAt: now}` so the sync checkpoint catches deletions — on live rows only (`liveOnly`: `{ $and: [filter, { deletedAt: null }] }`, so a tombstone is never re-stamped and re-synced), answering with a `deletedCount` (`asDeleteResult`). `findOneAndReplace` is stamped like `replaceOne` (it used to skip the wrapper, so its writes never synced); the three replace paths share `replacementWrite`, which validates a replacement without the engine stamps it cannot know (`validateReplacement`: a full-document check with stand-ins for `createdAt`/`deletedAt` — without them it refused `findOneAndReplace({ _id }, { name })` on a `dbValidation` model; stand-ins, not `.partial()`, which zod v4 refuses on an object schema carrying a refinement, so the schema's refinements still run; a `$set`/`$setOnInsert` patch is checked against `fieldsOnly(schema).partial()`, the fields without the object's refinements); bulkWrite's rewritten soft deletes keep the op's `collation`/`hint`. Walkers of filters and expressions share `runtime/plainDocument`'s `isPlainDocument` (not an array, Date, RegExp or BSON value). Known limit: offline, a `v.decimal128()` field nested inside an embedded document compared as a whole (`{ items: { price: 10 } }`) compares as text, not by value. bulkWrite's rewritten deletes are counted in its result's `modifiedCount`, not `deletedCount` (a BulkWriteResult cannot tell them apart from the batch's updates) — a known limit. A replace (`replaceOne`, `findOneAndReplace`, bulkWrite's `replaceOne`, upsert or not) keeps the stored row's engine stamps: it runs as an update pipeline (`keepingStamps`: `$replaceWith` of `$mergeObjects` — the row's `_id`, `createdAt: { $ifNull: ["$createdAt", now] }`, `deletedAt: { $ifNull: ["$deletedAt", null] }` under the replacement taken as a `$literal`, so the caller's own win; on an upsert that inserts, the `$ifNull`s give birth stamps), atomically; a plain replace lost both (a birth date of today; a tombstone undone on every client), and an upsert that matched overwrote them with birth stamps. Its change event is therefore usually an `update` — or still a `replace` when MongoDB logs the whole document (a diff not smaller than the document) — so a watch filtering on one of the two must take both, `operationType: { $in: ["update", "replace"] }` (a 4.0.0 breaking change for watches filtering `"replace"` alone); it needs MongoDB 4.2+. A time-series model stays a replace (birth stamps on an upsert). The wrapper is idempotent (`WRAPPED`): a db it already wrapped — `ctx.db` or `ctx.useDatabase(...)` given to a nested `ctx.runMutation` — is returned as is, so writes are not stamped, validated and encoded twice. Inserts store a stamped **copy** (stamps first, then the caller's fields — the stored shape tests pin); once `insertOne`/`insertMany` succeed, `stampCallerDoc` writes the stored `createdAt`/`updatedAt`/`deletedAt` and the generated `_id` (from `insertedId`/`insertedIds`) back onto the caller's own object, so a handler can return what it inserted without a re-read. A failed or validation-refused insert leaves the caller's object untouched; `bulkWrite` does not write back. A `WeakMap` (`writtenBack`) remembers the values mogobase wrote onto each object; `callerOwned(doc)` strips those (when still unchanged) at a later insert of the same object or of a copy spread from it (`spreadFrom`: its written-back `_id` instance plus one unchanged stamp and another field; an `_id` and stamps set one by one are kept) — and inside an update's `$set`/`$setOnInsert` (`ownedArgs`, for updateOne/updateMany/findOneAndUpdate and bulkWrite's update ops; the object itself, or a copy spread from it — recognised by the written-back `_id` instance plus at least one unchanged written-back stamp and some field beyond `_id` and the stamps, `writtenBackById`/`spreadFrom`; an `_id` (and stamps) named one by one is a deliberate reference and kept), where the written-back `_id` is an immutable-field error on another row and its `createdAt` would overwrite the target's own — only those two are left out of an update (`UPDATE_STRIPPED`), never `deletedAt`, so `$set: { ...row, deletedAt: null }` restores a soft-deleted row; NOT in a filter (`deleteOne(inserted)` targets exactly that row by its visible `_id`) and NOT in a replacement (replacing a row with its own object keeps its `createdAt`; another row's `_id` fails loudly) — while caller-set values are kept. Handlers that need a true hard-delete must reach through `ctx.db.model(name).collection.deleteOne(...)` directly. When the model has `dbValidation: true`, the same wrapper validates each write against the model's zod schema **after stamping** (so engine timestamps are present in the validated payload) and **before** the underlying call: `insertOne`/`insertMany` and full-replace updates run as full-doc parses; `$set` and `$setOnInsert` run as partials; aggregation-pipeline updates are skipped (no generic way to statically check the result shape). Validation failures throw `[mogobase] Validation failed for <model>.<op>: <path: msg; …>` synchronously — `await coll.insertOne(...)` in a handler catches it as a normal rejection. **For time-series models** (`isTimeseries(name) === true`), the wrapper changes shape: inserts skip the `deletedAt:null` stamp (still adds `createdAt`/`updatedAt`); `deleteOne`/`deleteMany`/`findOneAndDelete` always pass through to MongoDB's native delete regardless of `sync` (timeseries models are sync-incompatible by definition). **Decimal128 codec.** When a model's schema declares one or more `v.decimal128()` fields (`schemaHasDecimal128`), the same wrapper transparently encodes canonical decimal strings → BSON `Decimal128` on writes (schema-guided: `insertOne`/`insertMany`/full-replace docs, plus `$set`/`$setOnInsert` operator and dotted-path keys; **after** validation so the zod check still sees the string) and decodes `Decimal128` → string on reads (schema-agnostic deep walk over `findOne`/`findOneAndUpdate`/`findOneAndDelete` results and lazily through `find`/`aggregate` cursors, so the wire/handler form stays a plain decimal string while MongoDB stores the true numeric type — numeric `$gt`/`$sum`/`$avg`/cross-type comparison just work). Models with no decimal field skip both walks entirely (zero overhead). Codec primitives live in browser-safe `src/runtime/decimal.ts`; only the autoStamp wrapper imports `Decimal128` from `mongodb`.
- `hono.ts` — legacy HTTP app used by the standalone dev server (`mogobase dev`). Same `/api/handlers` GET/POST shape, plus `/api/sync` POST (`?action=pull|push`) that delegates to `pullChanges` / `pushChanges`.
- `ws.ts` — legacy Hono WebSocket wiring used by `mogobase dev`. Same message protocol as `attachWs.ts`, including the three sync message types.
- `start.ts` — Node entry for `mogobase dev`. Loads `.env` / `.env.local` from cwd, scans `./mogobase/` for `.ts` files, imports each, and calls its default export with the Hono `app`. Port from `MOGOBASE_PORT` (default `4000`). **This is only used when consumers want a standalone mogobase server — the Next.js path (`server.ts` template) replaces this.**

### DB (`src/db/`)

- `index.ts` — `MogobaseDB` singleton. `connect()` uses `MONGO_URI` / `MONGO_DB` (defaults `mongodb://localhost:27017` / `mogobase`). `defineModel(name, schema?, options?)` creates the collection if missing, stores the schema in `_schemas`, registers `options` (`indexSpecs`, `clientFields`, `sync`, `timeseries`) in `_options`, and applies indexes — including the engine stamp indexes `mogobase_updatedAt_1` / `mogobase_deletedAt_1` / `mogobase_createdAt_1` (Mongo no-ops on duplicate creates; **skipped for time-series models**, see below). Which stamp indexes a model builds comes from the runtime option `stampIndexes` (`getStampIndexFields(name)`; default all three, `false` none, `{ createdAt: false }` skips one; sync needs `updatedAt`). mogobase never drops an index on its own: `DB.diffIndexes(model, { dbName? })` returns `{ declared, actual, missing, conflicting, undeclared }` (pure matching in `src/db/indexes.ts`: by key — fields, order, direction — not name; each spec takes its exact match of its own name first, then any exact match, then what is left on its key (a conflict), and a spec whose exact match another spec took declares it again — present, not missing; a declared text index matches the collection's text index; when two indexes share a key the one whose options agree wins; a spec without a collation is compared against the collection's default collation, which MongoDB builds it with; `_id_` and a time-series `{metaField, timeField}` index are never undeclared), and `DB.dropUndeclaredIndexes(model, { dbName?, dryRun?, keep?, shadow? })` drops `undeclared` (every one is tried; an index already gone is skipped; any other failure throws after the rest were tried, naming the failures and carrying `dropped` / `failed`) (which includes indexes created outside mogobase — hence `keep` and `dryRun`; in a database the model does not live in, where every index is undeclared, a real drop is refused unless `shadow: true`). Both also exist on views (bound to the view's database). Builds go through `_buildIndexes`: one `createIndexes` batch, and if MongoDB refuses it (a batch fails as a whole): when the error names one spec (`specNamedInError`: "E11000 … index: email_1", an options conflict), that spec is reported and the rest built together in one more batch; otherwise each spec is retried alone — so one bad spec cannot block the rest, and a unique spec over duplicates costs two collection scans per boot, not one per spec; every spec that still fails is logged (`failed to apply custom indexes|sync indexes for <model>`, unchanged) and passed to `DB.onIndexError(listener)` listeners as `{ model, dbName, spec, specs, error }` (a cluster failure — `isClusterError`: no primary, network, shutdown, Unauthorized — is NOT retried per spec; it is reported once with `specs` = the whole batch — or the specs a failover in the one-by-one loop left unbuilt — retried on a backoff — `INDEX_RETRY_DELAYS_MS` 15 s → 4 min, each delay jittered ±25% (`jittered`) so replicas that failed in one election do not retry in lockstep, through `_scheduleRetry`, test hook `_indexRetryDelaysMs`; pending retries are tracked in `_indexRetryTimers` and cancelled by `disconnect()`, which also bumps `_connectionEpoch` so a build in flight that fails afterwards neither retries nor reports — and reported again only if every retry fails) (listener throws are caught and warned; `_indexErrorListeners` is lazily created because the singleton is built with `Object.create`). `DB.indexReport({ dbNames?, models? })` runs `diffIndexes` for every registered model in every database it lives in (default databases: the default one + every `uri::db` in `_appliedModels` on the default URI + names in `databases` lists); each diff carries `exists`; each database's collections are listed once (`listCollections()`, for existence and default collation; 8 databases at a time) and passed to `_diffIndexes`; listings run 8 at a time, order kept; on a view it is bound to the view's database. `defineModel` (singleton and view share `_defineIn`) marks every database it builds in (its own + a `databases` list, built in parallel) as applied BEFORE awaiting, so a concurrent lazy `_ensureModelApplied` does not start a second build, and unmarks one whose build failed (`_buildMarked`), so the first use there builds again — and a build that failed for the cluster's sake (a time-series probe during an election) is retried on the same backoff, since the default database has no lazy build; a listed database's failure is logged, never failing the defineModel that asked for its own database; every `connect()` (the first, and again after `disconnect()`) builds the registered models once per model (`latestModelDefs()`, each field from the latest definition that set it — except `indexSpecs`, which add up: every distinct spec any definition declares, as main built every definition; the latest replacing the rest lost a file's unique index. A spec's identity is its key, its name (own or generated) and the options that make another index, in any key order (`specId`; not `background`/`v`/`hidden`, and undefined or `unique`/`sparse` false is none — one index spelled two ways was kept twice, and a fresh collection's batch was refused whole). The only registration warning is one name on two keys, refused by every MongoDB; other pairs the server decides, version by version, and `onIndexError` reports a refusal), and a model registered later is built from its merged definition too, so `_schemas` agrees with the registry's getters; `disconnect()` waits for a `connect()` in flight first, so its client is closed too, and a `connect()` called while a disconnect is under way waits for it (`_disconnecting`) and opens a fresh client; `defineModel` returns a handle on a database the model lives in (its first listed one when not the one asked); concurrent `connect()` calls share one in-flight connection (`_connecting`); one build retry chain per (database, model) (`_pendingBuildRetries`; while one is pending a lazy first use still builds, at most once a second — `FIRST_USE_RETRY_GAP_MS`, `_lastFailedBuild` — without starting another chain); `disconnect()` bumps `_connectionEpoch` before closing clients, so a build failing because its client is closing never reports — a model build carries the epoch it started on through every step (`_buildMarked` → `_applyModelToDb` → `_buildIndexes`) and skips the steps left after a disconnect; a time-series `createCollection` that loses that race (NamespaceExists) is taken as success when the collection found is a time-series one, and still warns when a regular collection got there first. Exports: default singleton, `Id` (`ObjectId`), `buildFilters` (from `buildMongoFilters`), and `DataLoaderGenerate(model, key="_id")` for batched lookups. The singleton publishes itself to `globalThis.__mogobase_db__.instance` on load so the browser-safe `src/server/handlers.ts` can read it without a static import (see Server section).
- **Time-series collections.** When `defineModel` is called with `timeseries: { timeField, metaField?, granularity?, bucketMaxSpanSeconds?, bucketRoundingSeconds?, expireAfterSeconds? }`, the internal `_applyModelToDb` path probes for the collection via `listCollections({name}, {nameOnly: true})` and — only if it does not yet exist — calls `dbHandle.createCollection(name, { timeseries: {...}, expireAfterSeconds })`. Existing non-timeseries collections of the same name are left alone (MongoDB cannot convert a regular collection into a timeseries one); the create error is logged as `failed to create timeseries collection …` and mogobase falls back to a regular handle. The auto sync-checkpoint indexes (`updatedAt`, `deletedAt`, `createdAt`) are intentionally skipped for timeseries models — sync is disallowed, and the metaField+timeField auto-index covers the common access pattern. Custom `indexSpecs` are still applied. Timeseries options flow through the same `onModel`-listener path as schemas: `runtime/models.ts:defineModel` puts them on the `ModelDef`, the listener forwards them to `db/index.ts:defineModel(name, schema, indexes, timeseries)`, and `MogobaseDBView.defineModel` accepts the same fourth argument so multi-DB consumers can declare timeseries on a view. Helpers `getTimeseriesOptions(name)` and `isTimeseries(name)` from `mogobase/runtime` expose the registry state to the autoStamp and sync layers.
- **Multi-database primitives.** The singleton holds five additional registries: `_clients: Map<uri, MongoClient>` (one pooled connection per URI, reused across views), `_views: Map<key, MogobaseDBView>` (cached views keyed by `${uri}::${dbName}`), `_rawAliases: Map<name, { uri, dbName }>` (named cross-cluster connections registered via `registerDatabase`), `_appliedModels: Map<key, Set<modelName>>` (per-DB lazy-index dedup), and `_resolver?: RequestResolver` (the optional per-request hook).
  - `setRequestResolver(fn | null)` — registers/clears the resolver. Signature: `(ctx: { headers?: any }) => string | null | undefined | Promise<…>`. Called once per request from `_runQuery`/`_runMutation`'s entry boundary via `_resolveActive(headers)`. Returning a string binds `ctx.db` to a view of that DB name on the default cluster; `null`/`undefined` keeps the singleton; throws are wrapped as `DB resolver threw …`.
  - `useDatabase(dbName)` — synchronous; returns a `MogobaseDBView` for the named DB on the default cluster. Uses the cached view if present, else creates one via `_getOrCreateView(uri, dbName)` which calls `_getOrConnectClient(uri)` (lazy `MongoClient.connect`) and stores it in `_views`.
  - `registerDatabase(name, { uri?, dbName })` — registers a named raw alias. `uri` defaults to the singleton's URI when omitted (rare; `useDatabase` already covers same-cluster). Throws if `name` is already registered.
  - `useRawDatabase(name)` — async; resolves the alias to a raw `mongodb.Db` via the same `_getOrConnectClient` pool. Throws `Raw database "<name>" is not registered` if the alias is missing. No autoStamp, no schema awareness — it is the unwrapped driver.
  - `_resolveActive(headers)` — internal. Runs the resolver (if any) and returns either the singleton or a `MogobaseDBView`. Wrapped in try/catch so resolver throws surface as `DB resolver threw <err>`.
  - `_ensureModelApplied(view, modelName)` — internal. Idempotent per `(uri, dbName)` set in `_appliedModels`; on first call for a model on a given DB, replays the schema's indexes against that DB's collection. Called from `MogobaseDBView.model(name)` so cold-path cost is bounded to the first access of each (DB, model) pair.
  - **`MogobaseDBView`** — lightweight wrapper sharing `_schemas` (and therefore `_options` / `getModelOptions`) with the singleton. Exposes `client`, `db`, `model(name)`, `defineModel(...)` (delegates to the singleton so registration stays global), `getSchema` / `getSchemas`. Tests rely on `(view as any).db._name` to read the bound database name.
  - **No sync support.** The sync engine still uses the singleton's default DB; `useDatabase` and `useRawDatabase` are server-side reads/writes only. Multi-tenant sync is out of scope for v1.
  - **Where a model lives.** `DB.livesIn(model, dbName)` decides whether mogobase builds a model's indexes (and time-series collection) in a database: the model's own runtime option `databases` (`string[]` or `(dbName) => boolean`, read via `getModelDatabases`), else the app-wide rule `DB.setModelDatabases((model, dbName) => boolean | null)` (set before `connect()`), else `true` (today's behaviour). It gates `defineModel` on the default DB, `MogobaseDBView.defineModel`, and the lazy `_ensureModelApplied` (which marks the pair applied only where the model lives: marked before the check, a first use before `setModelDatabases` or the declaring file stayed marked, and the model was never built there once the rule said it lived there). A `databases` list is also built eagerly at `defineModel` in each named database. `diffIndexes` declares nothing for a database the model does not live in, so a shadow's indexes show as `undeclared`. A watch follows it too: `modelWatchDbName` (`src/server/requestDb.ts`, used by both transports after attachWs's `watchDatabaseFor`) sends `ctx.watch(model)` to the model's one declared home when its `databases` is a one-entry list that is not the request's database. An explicit `ctx.watch(model, filter, { dbName })` (`WatchOptions.dbName`, split off by `splitWatchOptions`, never sent to the driver) wins over `watchDatabaseFor` and the home; Both transports decide through one `watchTarget(model, options, active, override?)` (`requestDb.ts`), which splits the options and picks the database, and `dbHandleFor(name, active)` turns the chosen name into a handle. Nothing here drops a collection or index.

### Runtime registry (`src/runtime/models.ts`)

- `defineModel(name, schema?, options?)` runs `withSyncFields(schema)` before storing the def. `withSyncFields` merges `{createdAt: v.number(), updatedAt: v.number(), deletedAt: v.number().nullable()}` into either a `ZodObject` (via `.extend`) or a plain shape object — sync timestamp fields **always override** any consumer-defined versions of those keys. Schema-less models receive just the three sync fields. This is what guarantees that handler authors don't have to declare timestamps and that the RxDB JSON-schema generator + WatermelonDB JSON-blob both see numeric timestamps for every model.
- `options` is `{ indexSpecs?, clientFields?, sync?, dbValidation?, timeseries? }`. The runtime registry stores the full options object alongside the schema and exposes `getModelOptions(name)` so both the server sync engine and the `filterClientFields` runtime util can read `clientFields` and the `sync: true` allowlist flag from a single source of truth. `timeseries: { timeField, metaField?, granularity?, bucketMaxSpanSeconds?, bucketRoundingSeconds?, expireAfterSeconds? }` opts the underlying collection into MongoDB time-series mode — `defineModel` rejects `sync: true` combined with `timeseries` at registration with `defineModel("X"): \`sync: true\` is incompatible with \`timeseries\`` because soft-delete tombstones can't propagate through time-series collections. `getTimeseriesOptions(name)` / `isTimeseries(name)` expose the flag to the autoStamp wrapper (skip `deletedAt:null` stamp on inserts, skip soft-delete rewrites on deletes) and the sync engine (reject pull/push/watch). `clientFields: string[]` is the visibility allowlist for both the sync engine (pull projection + push strip) and the `filterClientFields` runtime helper. `sync: true` is the explicit opt-in required by the default-deny sync gate. `dbValidation: true` opts the model into runtime validation of writes (default false): the autoStamp wrapper parses each insert/update payload against the model's zod schema and throws on type mismatch — see `autoStamp.ts` below. The registry also exposes `isValidationEnabled(name)` and `getModelZodSchema(name)` (which normalizes plain shape objects into `z.object(...)` so callers can `.parse()` or `.partial()` uniformly). **Auto-loader caveat**: the `npx mogobase install` template's `server.ts` only scans `./mogobase/*.ts` — if `sync: true` lives only in a file under `./mogobase-sync/`, the server never sees the opt-in and the sync engine throws `Model "X" is not configured for sync`. Either keep the `defineModel` call under `./mogobase/`, or extend the loader to walk both folders.
- `v.decimal128()` (in `src/runtime/decimal.ts`, attached to the `v` export from `src/server/handlers.ts`; zod/v4's default export is non-extensible so `v` is `{ ...z4, decimal128 }`, not a mutation of `z4`) — a branded zod string validating a canonical decimal string (`-?\d+(\.\d+)?`) that the autoStamp wrapper persists as a BSON `Decimal128` and reads back as a string (see `autoStamp.ts`). The brand is a `Symbol.for("mogobase.decimal128")` on the schema instance; it survives `.optional()`/`.nullable()` because those wrap (not copy) the inner instance and `isDecimal128Schema` unwraps `_def.innerType`. `decimal.ts` is browser-safe (no `mongodb` import) — it only walks schemas/values; the real `Decimal128` constructor is injected by the server-side wrapper. Exposes `isDecimal128Schema` / `schemaHasDecimal128` / `encodeDecimal128` / `encodeDecimal128Patch` / `decodeDecimal128Deep`.
- `filterClientFields(model, input)` (in `src/runtime/clientFields.ts`, re-exported from `mogobase/runtime`) — projects an online handler's return value through the same allowlist used by sync. Reads `getModelOptions(model).clientFields`; if undefined, returns `input` unchanged. Otherwise projects to `clientFields ∪ CLIENT_ENGINE_FIELDS`. Handles three input shapes: single doc → projected doc; array → array of projected docs; paginated `{results, hasNext, hasPrevious, next, previous}` → same shape with `results` projected. The intent is symmetry: setting `clientFields` once on `defineModel` covers both the WS/HTTP query path (via `filterClientFields` calls in handlers) and the sync transport (automatic).

### Runtime helpers (`src/runtime/env.ts`, `src/runtime/paging.ts`)

- `env.ts` — `isServer()` / `isClient()` based on `typeof window === "undefined"`. Used by isomorphic handlers to dispatch on runtime; `isServer()` is true in Node (Next.js custom server, route handler workers, SSR) and false in any browser context.
- `paging.ts` — browser-safe polyfill of `mongo-cursor-pagination`'s default-exported `MongoPaging.find(col, params)`. Operates on any `find(filter).toArray()`-shaped collection (`RxMongoAdapter`, `WatermelonMongoAdapter`). Pulls the full matched set, then sorts/filters/slices in JS — adequate for per-user offline / sync datasets, not for million-row server queries. Same return shape as upstream (`{results, previous, next, hasPrevious, hasNext}`); cursor tokens are `base64url(JSON.stringify(value))` (plain JSON, not BSON-EJSON), with the standard `_id`-cursor → encoded value, non-`_id` cursor → `[fieldValue, _id]` shape. Supports `paginatedField`, `sortAscending`, `sortCaseInsensitive`, `next` / `previous`, `fields` projection, dotted-path field access. A `paginatedField` the collection declares decimal (`decimalFields`, which both offline adapters expose from the model's `decimal128Paths`) is ordered and paged by value, as the server's Decimal128; anything else as before (numbers by value, the rest as text). Mirrors upstream's `prepareResponse` semantics for `hasPrevious` / `hasNext`. The `find` function is exported both via `export const MongoPaging = { find }` and `export default MongoPaging` so handlers can use either named or default-import patterns. **Polyfill cursors and upstream BSON-EJSON cursors are not interchangeable**, but each side stays consistent within its own page sequence — which is all the hook needs.

Both helpers are re-exported from `mogobase/runtime`. The intended pattern for paginated handlers that run in both modes is:

```ts
import { isServer, MongoPaging as MongoPagingPolyfill } from "mogobase/runtime"
import MongoPaging from "mongo-cursor-pagination"
const Pager = isServer() ? (MongoPaging as any) : MongoPagingPolyfill
return Pager.find(ctx.db.model(name), { query, paginatedField: "_id", ...paginationOpts })
```

### Client (`src/client/`)

- `hooks/` — React hooks (`useQuery`, `useMutation`, `usePaginatedQuery`). The routing rule across all three: `if (online && !sync) → WS/HTTP`; `else if (ready && clientDB) → run handler against clientDB and re-run on clientDB.observeChanges(name)`. The fallback branch is reused for both `online={false}` and `online && sync` — same `runQuery` / `runMutation` from `mogobase/server` (pure, browser-safe). The hooks never import any backend module — they read `clientDB` and `sync` from React context. URLs are same-origin (derived from `window.location`), with `NEXT_MOGOBASE_URL` / `MOGOBASE_URL` env override for SSR or split-origin deploys. Also compiled into `lib/` and re-exported from the package root.
- `sync-types.ts` — wire-protocol types shared by client and server: `SyncDoc` (numeric `updatedAt`, `deletedAt`, `_deleted` flag), `SyncPullResult`, `SyncPushResult`, `SyncOptions` (`wsUrl`, `getAuth`, `models`, `conflictResolver`, `batchSize`), `SyncHandle` (`status`, `cancel`, `onStatusChange`). All timestamps are numeric ms. Browser-safe — no Node imports.
- `provider.ts` — `MogobaseProvider` / `useMogobase` context. Takes `online`, `handlers` (async loader), `dbName`, `clientDB`, `sync` (default `false`), and `syncOptions`. The provider holds **zero references** to either offline backend — direct or dynamic. The boot effect treats `useClientDB = !online || (online && sync)` as the trigger to run `clientDB.connect(dbName)`, the handler loader, and replay each registered model into `clientDB.defineModel(...)` — once, from its merged definition (`defineRegisteredModels`: `latestModelDefs()`, as the server builds it; replaying every raw definition let a later schema-less one hand the client a timestamps-only schema). After ready, when `online && sync`, it calls `clientDB.startSync(syncOptions)` and stores the `SyncHandle` in a ref so it can be cancelled on unmount or dep change. Throws a clear error if the path needs `clientDB` but none was provided. **`syncOptions` is in the effect's dep array — callers must memoize it (module scope or `useMemo`) to avoid tearing down + restarting sync on every render.** `MogobaseClientDB` is exported as a structural type that includes optional `startSync` / `stopSync` so importing it does not pull rxdb / watermelon into the bundle.
- `db/` — pluggable offline backends. The top-level `db/index.ts` re-exports the RxDB backend so consumers can `import RxClientDB from "mogobase/client-db"`.
  - `db/rxdb/` — `MogobaseClientDB` + `RxMongoAdapter` over RxDB + Dexie. `observeChanges(name)` wraps `collection.$` for reactivity. `defineModel` on a model already built returns its adapter as built (the collection keeps its first JSON schema, and the adapter its decimal fields). Filters run in RxDB's own query engine, which compares a `v.decimal128()` field's decimal strings as text (`{ amount: { $gt: 10 } }` does not match "12.50"): a known limit, unlike the Watermelon adapter, whose matcher compares them by value.
  - `db/watermelon/` — `MogobaseWatermelonDB` + `WatermelonMongoAdapter` + `filters.ts` (JS-side Mongo matcher + update applier). Each model is one table with `data` (JSON blob) + `deleted_at` (indexed) columns; filters are evaluated in JS on the decoded blob — by `runtime/filterMatcher` with `{ numericStrings: <the model's decimal fields> }` (`decimal128Paths(schema)` from `runtime/decimal.ts`, passed to each `WatermelonMongoAdapter`), so a `v.decimal128()` field (its decimal string here, a Decimal128 on the server) compares with a number by value and sorts by value, as on the server — and only those fields: any other string stays a string (`{ zip: 2134 }` never finds "02134"); the shared hub matches without it, as MongoDB does. `observeChanges(name)` wraps `Database.withChangesForTables([name])` and **skips the replay-on-subscribe emission** so `useQuery` doesn't loop on mount. WatermelonDB requires all `defineModel` calls to occur **before** the DB is first accessed; `defineModel` throws if called after `_ensureDb()` for an unknown model, but is idempotent for already-registered models (safe under React strict-mode double-mount).
    - **Cross-tab sync**: unlike RxDB (which has its own BroadcastChannel layer), LokiJS is purely in-memory per tab and doesn't observe IndexedDB peer writes. To fix this, `MogobaseWatermelonDB` opens a `BroadcastChannel("mogobase-watermelon-<dbName>")`. Every adapter mutation (`insertOne`/`insertMany`/`updateOne`/`updateMany`/`deleteOne`/`deleteMany`/`hardDeleteOne`) posts `{ table, op: "upsert", doc }` or `{ table, op: "hardDelete", id }` after writing. Incoming messages are applied through `_applyUpsert` / `_applyHardDelete` on the target adapter — these helpers look up the record by id directly (bypassing the soft-delete filter so a peer's `deletedAt` can travel through), and set `_applyingRemote = true` around the write to prevent echo loops. The resulting Watermelon write fires `withChangesForTables([name])` in the receiving tab so `observeChanges` subscribers (including `useQuery`) refresh naturally. No conflict resolution — last-writer-wins by message order.
- Both backends conform to the same interface: `connect(dbName)`, `defineModel(name, schema?, indexes?)`, `model(name)` → Mongo-shaped adapter, `observeChanges(name)`, `startSync(options)` / `stopSync()` (sync mode), default export = singleton. Hooks reach into neither backend's internals. Both `rxdb` and `@nozbe/watermelondb` are **optional peer dependencies** — only the consumer that actually imports `mogobase/client-db` (or `…/watermelon`) needs to install the matching package. An online-only consumer (no `sync`, no offline) installs neither.
- `db/rxdb/sync.ts` — RxDB sync engine. Uses `replicateRxCollection` from `rxdb/plugins/replication` (dynamically imported, kept out of the base bundle). One shared `WebSocket` to `/ws`; per collection, a `rxjs.Subject` feeds the replicate stream — `"RESYNC"` triggers a re-pull. Pull/push handlers send `sync-pull`/`sync-push` over WS and resolve when the matching `SyncPullResult`/`SyncPushResult` arrives (multiplexed by `model` field). Checkpoint flows through RxDB as `{ts: number, updatedAt: number}` and is unwrapped to a plain numeric ms internally. WS close → reject pendings, RESYNC every subject, reconnect after 3s.
- `db/watermelon/sync.ts` — WatermelonDB sync engine. Uses `synchronize()` from `@nozbe/watermelondb/sync` (dynamic import). One shared WS, per-model checkpoint `Map<string, number | null>` (we ignore `synchronize`'s single `lastPulledAt` and use our own per-model). **Critical detail**: `synchronize` only fires on WS open and incoming `sync-stream` events — it has no built-in observer for local mutations. To push user writes promptly, the engine subscribes to `wdb.withChangesForTables(targetModels)` and triggers `runSync()` on each emission, with two guards: `inSyncCycle` (set true around `synchronize` so the pull-apply path's writes don't re-trigger a sync) and a `primed` flag (skips `withChangesForTables`'s replay-on-subscribe value). Two known limitations: (1) `synchronize` writes through Watermelon's internal `_applyChanges`, bypassing `WatermelonMongoAdapter` — so sync-applied writes do NOT post to the cross-tab `BroadcastChannel`. Each tab pulls independently, by design. (2) `synchronize` does a full pull per cycle; for >10K records per model the initial sync is slow.
- `api/handlers/route.ts` — Next.js App Router route template. **In-process**: imports `runQuery` / `runMutation` from `mogobase/server` and the `DB` singleton from `mogobase/db`, calls them directly.
- `api/sync/route.ts` — Next.js HTTP-fallback route template for sync. `POST /api/sync?action=pull|push` body `{model, checkpoint?, batchSize?, rows?}`. Imports `pullChanges` / `pushChanges` from `mogobase/server/sync` and forwards a `syncPolicy` arg on every call. The scaffolded template ships with a placeholder `getSession` and a deny-all `syncPolicy`; consumers must wire in their real auth + policy before enabling sync (typically by importing the same `mogobase/syncPolicy.ts` module that `server.ts` uses). Default sync transport is WS; this route exists for environments where WS is unavailable. Always copied by `mogobase install` (harmless when sync isn't enabled).
- `server.ts` — Custom Next.js server template. Creates Node `http.Server`, delegates to Next.js `getRequestHandler()`, calls `attachMogobaseWebSocket(server)`, and loads consumer's `./mogobase/*.ts` files at boot to trigger handler registration. This file is excluded from `tsc` compilation (imports `next` which is a peer dep) and shipped as raw source.
- All four (`hooks/`, `api/handlers`, `api/sync`, `server.ts`) ship as raw `.ts` source via `files` in `package.json` so `mogobase install` can copy them into the caller.

### Dev CLI (`src/dev/`)

- `index.ts` — `bin` entry. Dispatches on first arg: `dev` spawns `npx tsx watch ./node_modules/mogobase/lib/dev/start.js` in the consumer's cwd; `install` calls `install.ts`; `mcp` dynamically imports `../mcp/start.js` to boot the stdio MCP server.
- `install.ts` — `install(options)` is the callable entrypoint used by both the CLI and the MCP `mogobase_install` tool. Takes `{ cwd?, logger? }` and returns an `InstallSummary` (`created` / `overwritten` / `skipped` / `nextSteps`). Copies four things into the caller's Next.js project:
  1. Hooks → prefers existing `src/hooks/` or `hooks/`, else creates `src/hooks/` (or `hooks/` if no `src/`). Rewrites relative imports (`../provider`, `../../runtime`) to package imports via `rewriteHookImports`.
  2. Handlers route → installs to `src/app/api/handlers/route.ts` if `src/app/` exists, else `app/api/handlers/route.ts`.
  3. Sync route → `src/app/api/sync/route.ts` (or `app/api/sync/route.ts`). Always copied even if sync isn't used — harmless idle.
  4. Custom server → `server.ts` at project root.
  Also creates `./mogobase/` folder for consumer's handler files. Files are **overwritten unconditionally** — no interactive prompting; call `mogobase_check_setup` first (or inspect before running) to avoid clobbering.
- Path resolution: `resolveMogobaseRoot()` probes `../..` and `../../..` relative to the running module so it works both from `lib/dev/` in a published install and from source during local tests.

### MCP server (`src/mcp/`)

- `start.ts` — boots an `McpServer` from `@modelcontextprotocol/sdk` with `{ resources, tools, prompts }` capabilities and connects it over `StdioServerTransport`. Name/version come from `readPackageVersion()` (reads the installed `mogobase` `package.json`). Entered via `mogobase mcp`.
- `tools/index.ts` — registers five tools:
  - `mogobase_install` — thin wrapper around `install()` from `src/dev/install.ts`; captures `logger` lines and returns them alongside the `InstallSummary`.
  - `mogobase_check_setup` — reports project type, presence of `server.ts` / route handler / `./mogobase/` / `<MogobaseProvider>` mount, `package.json` scripts+deps, and `MONGO_URI` / `MONGO_DB` across `.env*` files. Non-destructive; always call this before `mogobase_install`.
  - `mogobase_list_handlers` / `mogobase_list_models` — use `parseHandlers.ts` (a regex/AST-light scanner over `./mogobase/*.ts`) to enumerate `query`/`mutation`/`internalQuery`/`internalMutation` calls and `defineModel` calls with file + line.
  - `mogobase_inspect_handler` — returns ~30 lines of source context around a named handler. Accepts either `name` or `internal.name`.
- `resources.ts` — registers thirteen markdown guides at `mogobase://guide/<slug>` (`overview`, `setup`, `handlers`, `models`, `hooks`, `provider`, `offline-backends`, `sync`, `troubleshooting`, `scaling`, `configuration` — every option, environment variable and default, with how to choose values per project; keep it current when a default changes —, `protocol` — every `/ws` message and frame, for apps that write their own client — and `upgrading` — every breaking change between majors, each with a search that finds it in an app, the fix and the log line to check; add to it whenever a change breaks an app, it is what a project's AI agent follows to upgrade). `tests/unit/mcp/guides.test.ts` loads every registered guide. Reads from `lib/mcp/guides/` when installed, falls back to `src/mcp/guides/` during local dev — so the build script must copy `src/mcp/guides/*.md` into `lib/mcp/guides/`. The `sync` guide is the source of truth for the security model (default-deny allowlist, `clientFields` projection, `SyncPolicy` callback, server-owned timestamps, push batch cap, soft-delete invariant).
- `prompts.ts` — registers two prompts: `setup-mogobase`, that seeds the assistant with the correct onboarding workflow (check setup → read guides → propose + confirm → install), and `upgrade-mogobase`, that walks a major upgrade through the `upgrading` guide (find each change, fix, check the log, propose options; never re-run the installer over customised files).
- `guides/*.md` — source of truth for the long-form explanations surfaced via MCP resources. Prefer editing these over inlining large blocks of prose into tool descriptions.
- When adding a new tool, register it from `tools/index.ts` and keep the tool name prefixed with `mogobase_` for easy disambiguation in the MCP client. When adding a new guide, update the `GUIDES` array in `resources.ts` **and** ensure the `.md` file lands in `lib/mcp/guides/` via the build script (no separate `files` entry is needed — the copy step places it inside `lib/`).

### How a consumer uses this package (Next.js App Router)

1. `yarn add mogobase ws` and `yarn add -D @types/ws`. For offline or sync mode, also install the backend you want to use: `yarn add rxdb` (RxDB, default) or `yarn add @nozbe/watermelondb` (WatermelonDB). Pure-online consumers install neither.
2. `npx mogobase install` — copies hooks, `app/api/handlers/route.ts`, `app/api/sync/route.ts`, and `server.ts`; creates `./mogobase/`.
3. Update `package.json` scripts: `"dev": "tsx server.ts"`, `"start": "NODE_ENV=production tsx server.ts"`.
4. Add handler files in `./mogobase/*.ts` that call `query()`/`mutation()` at module scope.
5. Set `MONGO_URI` / `MONGO_DB` in `.env.local`.
6. Pick a provider mode:
   - **Online only**: `<MogobaseProvider online={true}>` — no `clientDB`, no offline package.
   - **Offline only** (`online={false}`): `<MogobaseProvider online={false} clientDB={RxClientDB} handlers={…} dbName="…">`. Hooks run handlers in the browser against `clientDB`.
   - **Local-first sync** (`online={true}` + `sync={true}`): `<MogobaseProvider online sync clientDB={…} handlers={…} dbName="…" syncOptions={…}>`. Hooks read/write through `clientDB`; a background engine continuously replicates with MongoDB over `/ws`. **Memoize `syncOptions`** — it's in the boot effect's dep array. Server-side: every model that participates must be declared with `defineModel(name, schema, { sync: true, clientFields: [...] })`, and `server.ts` must call `attachMogobaseWebSocket(server, "/ws", { syncPolicy })` with a real policy (the same module is imported by `app/api/sync/route.ts` for the HTTP fallback). Without these, the engine returns `Model not configured for sync` or `Forbidden`.

## Conventions specific to this repo

- Singletons are the norm (`Handlers`, `MogobaseDB`, `WebSocket`). Do not introduce per-request instances without a clear reason — existing code relies on the singletons being shared across `hono.ts`, `ws.ts`, and consumer-registered handlers.
- Handler names beginning with `internal` are routed to the `_queries`/`_mutations` maps and stored with an `internal.` prefix — preserve this behavior when editing `handlers.ts`. A second `internalQuery`/`internalMutation` of one name warns and replaces the first (its duplicate check never fired before 4.0.0; a throw, as `query()`/`mutation()` do, would stop such an app from booting).
- **Timestamps on the wire and in storage are numeric ms (`Date.now()`), never ISO strings.** `createdAt`, `updatedAt`, and `deletedAt | null` are auto-injected on every model by `withSyncFields` in `runtime/models.ts` and auto-stamped on every write by `wrapDbWithAutoStamp` (server) and the client adapters. Don't reintroduce string timestamps; the sync checkpoint and the RxDB JSON-schema bounds (`minimum: 0`, `maximum: 8640000000000000`, `multipleOf: 1`) all assume numbers.
- `_id` for sync-mode collections is a string (UUID from the client adapter's `genId()`). MongoDB collections used with sync must accept string `_id`; existing collections with `ObjectId` `_id` are incompatible.
- When adding files that must be shipped as source (not compiled), update the `files` array in `package.json` — compiled output only covers what `tsc` emits into `lib/`.
- The `baseUrl`/`rootDir` deprecation warnings from `tsc` are pre-existing and do not block `build`; leave them alone unless explicitly asked to migrate.
- **Sync is default-deny.** Adding sync to a model requires three changes that must travel together: (1) `defineModel(name, schema, { sync: true, clientFields: [...] })` on the **server** side (i.e. inside a `./mogobase/*.ts` file the custom `server.ts` actually imports — not split off into `./mogobase-sync/`), (2) a `SyncPolicy` branch returning `{allow: true, filter, transform}` for the model, and (3) the policy module wired into both `attachMogobaseWebSocket(..., { syncPolicy })` and the HTTP fallback `app/api/sync/route.ts`. Skipping any one is the single most common cause of "client gets 403 on every pull".
- **`clientFields` is a contract.** Once set, server-only fields never reach the client (pull-side projection) and clients can't write them (push-side strip). The same allowlist drives `filterClientFields(model, doc)` in online handlers, so adding a new field that should be visible client-side requires updating `clientFields` — it won't simply leak through.
- **Server-owned timestamps.** `pushChanges` always overrides client `createdAt`/`updatedAt`/`deletedAt` with `Date.now()` (or preserves `existing.createdAt` for updates). Don't try to round-trip these through the client.
- **`dbValidation` is gated to handler writes only.** The flag wraps writes that go through `_runMutation`'s autoStamp Proxy. Sync push (`pushChanges` in `src/server/sync.ts`) writes to the raw collection and is **not** validated by this flag — it relies on the policy `transform` callback for shape enforcement. So a model can have `dbValidation: true` for handler safety while still depending on `transform` to gate sync-push payloads.
- **Time-series models are sync-incompatible and have reduced auto-stamp.** `defineModel(name, schema, { timeseries: { timeField, … } })` makes mogobase create the collection via `db.createCollection(name, { timeseries: {…} })` on first apply (and skip the `updatedAt`/`deletedAt`/`createdAt` auto-indexes — they are not needed because sync is forbidden). The autoStamp wrapper stops adding `deletedAt: null` to inserts and passes `deleteOne` / `deleteMany` / `findOneAndDelete` straight through to MongoDB. Sync entry points (`pullChanges`, `pushChanges`, `streamChanges`) reject timeseries models with `Model "X" is a time-series collection. Sync is not supported …`. `buildMongoFilters` still works transparently — the `{deletedAt: null}` predicate it always injects matches docs that don't have the field. `mongo-cursor-pagination` paginates timeseries collections correctly by `_id`. **You cannot convert an existing regular collection into a timeseries one** — `createCollection` errors when a non-timeseries collection of the same name already exists; drop or rename it first.
